## 1. TL;DR

- Every frontier-style open stack is converging on the same decomposition: a rollout engine (SGLang or vLLM) behind an HTTP/Ray interface, a Megatron/FSDP trainer, a weight-sync layer, and a reward layer that is just another async service. Colocated-with-sleep is the default for small clusters; disaggregated plus async is what labs use when long-tail (agentic) rollouts dominate.
- The off-policy gap has two independent sources that are now handled by the same machinery: (a) temporal staleness (async, partial rollouts) and (b) numerical mismatch between rollout and training kernels (BF16/FP8/MoE routing). The shared fix is to store the behavior-policy log-prob (and weight version) per token at sampling time, then apply a decoupled-PPO / TIS / MIS / rejection-sampling correction in the loss. slime, verl and AReaL all implement this; the knobs differ.
- Where mismatch cannot be corrected away, labs remove it: FP32 LM head (MiniMax, ScaleRL), FP16 instead of BF16 (Sea AI Lab paper), batch-invariant deterministic inference plus matched training kernels (Thinking Machines, SGLang, slime GLM-5 alignment path), and rollout routing replay (R2/R3, DeepSeek-V3.2 "Keep Routing") for MoE.
- Long-tail handling has three families: over-provision and abort (APRIL, slime `over_sampling_batch_size` + `abort`), pause/continue across weight updates (SGLang `pause_generation` modes, vLLM `pause_generation(mode="keep")`, PipelineRL in-flight updates, verl partial rollout, Kimi K3 lambda-fraction pause), and scheduling (Seer divided rollout, Laminar repack, MiniMax Forge windowed FIFO, verl dynamic hybrid replicas). Each has a documented selection-bias cost (fast/easy samples are over-represented).
- Weight sync is a solved-ish engineering problem with a menu: CUDA-IPC flattened-bucket (colocated), NCCL broadcast groups (disaggregated), checkpoint-engine / Mooncake RDMA P2P (elastic, ~20 s for 1T params per Moonshot), disk and XOR+zstd delta checkpoints (cross-datacenter, new in slime). None of this matters when the reward oracle takes minutes to days; it matters a lot for LLM-scale loops.
- Sandbox fleets are the agentic analogue of an expensive oracle. Kimi K3 reports 51.2M sandboxes from 1.5M images with Firecracker pause/resume/fork/snapshot (133 ms save, 49 ms resume, 6.5x memory overcommit) because agents wait on the model about 98% of sandbox lifetime. These primitives (pause when waiting, fork for side-effect-free grading) transfer directly to simulators and lab workflows.
- For biology with slow rewards (ESMFold seconds, AF3/docking minutes, MD hours, wet lab days) the right architecture is "macro-synchronous, micro-asynchronous": a persistent job queue for oracle calls, per-sample behavior log-probs and version stamps, a multi-fidelity reward cascade, selection-bias-aware importance weights, and censoring-aware handling of timeouts. Section 5 details this and flags genuinely new ideas.

## 2. Per-project sections

### 2.1 SGLang as RL rollout engine (`sgl-project/sglang`)

What it is: the de facto rollout engine for slime, Miles, AReaL, ROLL, verl (docs: `docs/docs/references/post_training_integration.mdx`). The RL-specific surface is documented in `docs/docs/advanced_features/sglang_for_rl.mdx` and implemented under `python/sglang/srt/model_executor/model_runner_components/weight_updater.py`.

RL features read in code/docs:
- Sleep/wake: `--enable-memory-saver` plus `POST /release_memory_occupation` and `/resume_memory_occupation` with `tags` of `kv_cache` and/or `weights`; built on `torch_memory_saver` so virtual addresses are preserved and CUDA graphs keep replaying. The release call asserts the engine is idle.
- Three refit paths: `update_weights_from_disk` (simplest, elastic, checkpoint as source of truth; params include `abort_all_requests`, `keep_pause`, `recapture_cuda_graph`, `flush_cache`, `weight_version`), `update_weights_from_tensor` (colocated, CUDA IPC, serialized with `MultiprocessingSerializer`, `flattened_bucket` load format) and `update_weights_from_distributed` with `init_weights_update_group` / `destroy_weights_update_group` (NCCL group of trainer rank 0 plus all engine ranks).
- Weight-update session: `begin_weight_update` / `end_weight_update` bracket many bucket updates so quantized layers (Marlin repack, MXFP8 shuffles) are post-processed once per refit, not once per bucket. An update outside a session is rejected with HTTP 400.
- `pause_generation` modes: `abort` (default; returns requests to the caller), `retract` (move running requests to waiting; KV can be flushed and recomputed), `in_place` (freeze scheduler state; a later `flush_cache` fails). Followed by `continue_generation`. This is the primitive behind APRIL-style partial rollout and PipelineRL-style in-flight updates.
- Per-token weight-version attribution: `meta_info.weight_versions` returns half-open output-token ranges per version, e.g. `[{"version":"41","start":0,"end":57},{"version":"42","start":57,"end":128}]`. This is exactly what a decoupled-PPO loss needs for mixed-version trajectories.
- Deterministic inference: `--enable-deterministic-inference` (FlashInfer, FA3 or Triton attention; CUDA graph, chunked prefill, radix cache (not on FlashInfer), non-greedy sampling via per-request `sampling_seed`), built on Thinking Machines' batch-invariant operators. Docs explicitly say true on-policy also requires matching kernels on the training side (pointer to Miles `examples/true_on_policy`).
- MoE routing capture: `enable_return_routed_experts` and `state_capturer/routed_experts.py` (`RoutedExpertsCapturer`, host buffer, DP-rank-aware slicing, fused shared-expert columns dropped on return) feed R3.
- Remote-instance weight loading over Mooncake TransferEngine (`remote_instance_weight_transporter.py`: `TransferEngine().initialize(local_ip, "P2PHANDSHAKE", protocol, device)`), i.e. RDMA P2P weight copy from a peer engine for elastic scale-out.
- SGLang Model Gateway: cache-aware load balancer and fault-tolerant router, described as used in GLM-4.5+ training; also the documented way to run reward servers as independent, failover-capable services.

vLLM comparison (blog/docs, not code-read): native RL APIs (2026-05-28) add a four-phase weight-transfer API (`init_weight_transfer_engine`, `start_weight_update`, `update_weights`, `finish_weight_update`) with NCCL and IPC backends, and `pause_generation(mode="abort"|"wait"|"keep")` with a two-phase pause to avoid DP/EP deadlocks. Mode "keep" is what PipelineRL uses.

### 2.2 slime (`THUDM/slime`, used for GLM-4.5 to GLM-5)

What it is: Megatron training plus SGLang rollout orchestrated by Ray; Sample objects carry `rollout_log_probs`, `loss_mask`, `weight_versions`, `status` (`slime/utils/types.py`).

Algorithm/correction (read: `slime/utils/ppo_utils.py`, `slime/backends/megatron_utils/loss.py`, `examples/train_infer_mismatch_helper/`):
- `importance_weights(ratio, mode, low, high)`: `tis` = `clamp(ratio, low, high)` (defaults 0 and 2.0); `mis` = keep ratio only inside `[0.5, 5.0]`, else weight 0 (a mask, IcePop-style).
- Three loss modes documented in `examples/train_infer_mismatch_helper/README.md`: standard PPO (old log-prob recomputed in Megatron), "bypass" (`--use-rollout-logprobs`: rollout log-probs as old policy, skip one forward pass over all trajectories), and decoupled 3-policy PPO (`--use-tis`, proximal = Megatron recompute, behavior = SGLang). Config file `mis.yaml`: IS level `token|sequence|geometric`, mode `truncate|mask|clip`, `tis_upper_bound: 2.0`, `tis_lower_bound: 0.5`, rejection sampling with independent bounds, per-token veto `rs_veto_threshold: 1.0e-4` (zero the whole sequence if any token ratio is below it), `tis_batch_normalize: true` (normalize weights to mean 1).
- `--get-mismatch-metrics` logs `mismatch_kl`, `mismatch_k3_kl`, PPL ratios and `train_rollout_logprob_abs_diff` without changing the loss; this is the recommended first step before turning corrections on.
- Score centering (`slime/utils/score_centering.py`) with REINFORCE loss and top-k rollout logprobs, and `rollout_top_p_log_probs` in the batch: the sampler's truncated distribution is stored so the loss can use the same action space as sampling (cf. DeepSeek-V3.2 "Keep Sampling Mask").

Rollout design:
- `slime/rollout/sglang_rollout.py`: oversampling (`over_sampling_batch_size`), `dynamic_sampling_filter_path` hooks to drop zero-variance groups, an `abort()` that collects in-flight groups back into the data buffer when `--partial-rollout` is on, and `--mask-offpolicy-in-partial-rollout`, which sets `loss_mask=0` on tokens generated under an older policy and trains only on the freshly continued part.
- `slime/rollout/fully_async_rollout.py` and `fully_async_distributed.py`: a background asyncio worker keeps up to `sglang_server_concurrency` generations in flight across rollout boundaries; groups containing an ABORTED sample are pushed back into the buffer; a distributed `RolloutScheduler` collects from autonomous workers with bounded prefetch for backpressure, retires failed workers, and supports `pause(drain=True)`/`resume`/`state_dict` for checkpointing.
- Staleness is measured, not just bounded: `compute_staleness_metrics(samples, weight_version)` in `slime/observability/rollout_metrics.py`, fed by `Sample.weight_versions`.
- PipelineRL-style mode is selectable: `--flush-cache-interval N` (default 1 = abort and flush every sync); other values pause in place and keep unfinished sequences, auto-select fully-async rollout and require separate training/rollout GPUs (`slime/utils/weight_sync.py::should_flush_cache`, `slime/utils/arguments.py` ~L340 and ~L2212).
- `straw` transport (`docs/en/advanced/straw.md`): filesystem-backed queues (JuiceFS) persisting prompt tasks, partial rollouts, completed samples and training batches; Ray only carries control messages. This is a durable job-queue pattern.
- Tracing and replay: `--save-debug-rollout-data`, `--load-debug-rollout-data`, `--debug-rollout-only`, `--debug-train-only`; trace viewer for reward/model-call spans.

Weight sync (read: `slime/backends/megatron_utils/update_weight/`): four transports. `update_weight_from_tensor.py` (colocated; per-bucket CUDA IPC via `FlattenedTensorBucket`, gather to one rank, `ipc_collect()` after each bucket; pause mode is `abort` when `flush_cache` else `in_place`), `update_weight_from_distributed.py` (one NCCL group per PP rank: trainer DP=TP=0 rank plus all engine GPUs; async `dist.broadcast` per tensor; a Ray lock prevents concurrent transfers deadlocking; EP all-gather then HF conversion on the PP source), `update_weight_from_disk.py`, and `update_weight_from_disk_delta.py` (documented in `docs/en/advanced/delta-weight-sync.md`: trainer keeps a CPU snapshot of HF tensors, publishes `new XOR old` (or overwrite) zstd level-1 compressed per version directory as a canonical HF checkpoint; every rollout host applies in place via `/pull_weights` with per-tensor xxh3-128 checksums and refuses out-of-order versions; reload through vanilla `update_weights_from_disk`).

Low precision (`docs/en/advanced/low-precision.md`): BF16 train + FP8 rollout is "stable" (blockwise 128x128 FP8 checkpoint; slime quantizes BF16 weights at update time using the `quantization_config` in `--hf-checkpoint`); FP8 KV cache via `--sglang-kv-cache-dtype fp8_e4m3`; INT4 QAT and FP8 train+rollout are beta/experimental. The LMSYS FP8-RL blog reports that for MoE the BF16-train/FP8-rollout discrepancy grows with model size and that unified FP8 reduces TIS clip fraction and log-prob gaps from 30B to 235B.

MoE (read: `slime/utils/routing_replay.py`, `slime/utils/routed_experts.py`, arguments `--use-routing-replay` (R2) and `--use-rollout-routing-replay` (R3)): R3 requests `return_routed_experts` per generation and replays the recorded top-k indices in the Megatron forward and backward passes; a `RoutingReplay` class asserts each recorded router was consumed exactly once in forward and backward (`assert_all_consumed`), and `validate_routed_experts_tensor` rejects all-zero layers rather than "replaying expert 0 everywhere" (a failure mode when pipeline-parallel SGLang stages do not aggregate captures). For GLM-5 an "ordered top-k" capture reproduces SGLang's `torch.topk(sorted=False)` order, because BF16 accumulation order over experts differs from Megatron's sorted order even when the selected expert set is identical.

Fault tolerance (`docs/en/advanced/fault-tolerance.md`): `--use-fault-tolerance`, `/health_generate` heartbeat (defaults: first wait 300 s, interval 10 s, timeout 5 s), stop unhealthy engine, restart after the current round and re-push weights. Explicitly out of scope: trainer-rank failure, which relies on checkpoints plus scheduler.

Agent environments: `examples/coding_agent_rl/` runs Claude Code or Codex inside E2B-compatible sandboxes (fresh sandbox per sample, diff graded in a second clean sandbox), with an Anthropic-API-compatible adapter that tokenizes each turn, keeps model-generated tokens at `loss_mask=1` only while later prompts stitch onto them, and forks a new trajectory branch when the prompt prefix diverges (sub-agents, auto-compaction) (`slime/agent/trajectory.py`).

GLM-5 report (arXiv 2602.15763, as summarized): GRPO plus IcePop-style double-sided mismatch masking (beta=2, eps_low=0.2, eps_high=0.28), group size 32, "direct double-sided importance sampling for token clipping", dropping off-policy and noisy samples, token-in-token-out, DP-aware routing, heartbeat fault tolerance. Reproducibility doc adds a GLM-5-only train/rollout log-prob alignment path (deterministic SGLang, batch-invariant DeepGEMM, DeepEP, patched Megatron).

### 2.3 verl (`volcengine/verl`)

Read: `verl/trainer/config/algorithm/rollout_correction.yaml`, `verl/trainer/ppo/rollout_corr_helper.py`, `docs/algo/rollout_corr.md`, `docs/advance/{fully_async,v1_async_trainer,determinism,dynamic_schedule,delta_weight_sync}.md`, `verl/checkpoint_engine/README.md`, `verl/experimental/{fully_async_policy,reward_loop}/`.

- Rollout Correction (author Yingru Li): config `rollout_is: null|token|sequence`, `rollout_is_threshold` (a float is a TIS upper bound; `"lower_upper"` is IcePop), `rollout_rs` with divergence-based filters such as `token_k1`, `seq_sum_k1`, `seq_mean_k3`, `bypass_mode` (false = decoupled 3-policy, true = 2-policy), bypass `loss_type: ppo_clip|reinforce`. The helper computes in log space with a fixed safety bound exp(+-20) and logs ESS, KL, chi-squared divergence and outlier fractions. The doc argues many PPO implementations wrongly treat pi_old as the behavior policy when pi_rollout differs, which is the core of the Fengyao/Yingru analysis. Cited follow-up: Trust Region Masking (arXiv 2512.23075).
- Async family: `one_step_off_policy`, `fully_async_policy` (Rollouter, MessageQueue, Trainer, ParameterSynchronizer; sample-level streaming; `staleness_threshold` as a fraction with `rollout_num = (1+staleness_threshold) * (trigger_parameter_sync_step * require_batches * ppo_mini_batch_size) - num_staleness_sample`; `partial_rollout` via sleep/resume; NCCL sync modeled on checkpoint-engine; reported 2.35x-2.67x on 128 GPUs for Qwen2.5-7B), and a V1 trainer (`trainer_mode: sync | colocate_async | separate_async`) with `TransferQueue`, partial-rollout client that keeps tokens and log-probs of aborted requests, retries with the newer model (trajectories can span versions), and a version-based `max_off_policy_threshold` (default 8).
- Dynamic hybrid scheduling (`dynamic_schedule/`): trainer-node GPUs host sleeping "hybrid" rollout replicas that wake when the sample queue is low (`deactivate_ratio` 0.3) and are put back to sleep (abort, remove from router first, then offload) before each train step; reported 15.3% end-to-end gain on Qwen3.5-35B-A3B. This is a template for sharing GPUs between a policy and an expensive oracle.
- Checkpoint engine abstraction: `naive`, `nccl`, `hccl`, `nixl`, `mooncake`, `kimi_ckpt_engine` (offload weights to CPU, Mooncake P2P to one rollout worker, then broadcast); benchmark on 4x8 H100 with 400 Gbps IB: NCCL about 7 s for Qwen3-30B-A3B, Mooncake 5.93 s. Plus a delta checkpoint engine.
- Reward layer (`reward_loop/`): `RateLimitedRewardManager` implements three layers of global limiting (concurrency semaphore, requests per minute and tokens per minute via `AsyncTokenBucket`) for API-based judges; `RemoteRewardManager` runs scoring in separate Ray CPU processes; reward models can be served through an inner SGLang router.
- Determinism: `full_determinism: true` for rollout, actor and reward model, requires vLLM batch invariance or `max_num_seqs=1`, and the older (V0) trainer because V1 collects in completion order.

### 2.4 AReaL (`inclusionAI/AReaL`)

Read: `areal/infra/staleness_manager.py`, `areal/trainer/ppo/actor.py`, `areal/api/cli_args.py`, `areal/engine/sglang_remote.py`, `areal/infra/sandbox/`.

- Staleness control is an explicit admission formula: `capacity = min(max_concurrent_rollouts - running, (max_staleness + current_version + 1) * consumer_batch_size - (accepted + running))`; pending limit `(max_staleness + 1) * consumer_batch_size`; on checkpoint recovery `accepted` is reset to `version * batch` to avoid a submission burst. Default `max_head_offpolicyness=0` (synchronous); end-to-end determinism is only claimed at 0.
- Per-token `versions` are stored with each rollout. For decoupled PPO the proximal log-prob can be (a) recomputed by a forward pass, (b) approximated without a forward pass by version-aware interpolation: `alpha = (v_prox - v_behave) / (v_theta - v_behave)`, `logp_prox = old + alpha * (new - old)` (log-linear) or an arithmetic mix in probability space (`compute_prox_logp_approximations`), (c) reuse training log-prob. Extras: M2PO (`m2_threshold` second-moment masking), CISPO, SAPO (incompatible with the decoupled loss), rejection sampling config.
- Pause is implemented as two HTTP requests, first default-abort then `mode="in_place"`, because the abort path never reaches the scheduler's paused flag that the colocate loop watches (comment in `sglang_remote.py::get_pause_requests`).
- Daytona sandbox runner (`areal/infra/sandbox/`) for code execution.
- Paper (arXiv 2505.24298, as summarized): fully async, up to 2.77x speedup over synchronous at equal GPUs with matched or better accuracy, interruptible generation plus staleness-aware PPO.

### 2.5 PipelineRL (`ServiceNow/PipelineRL`, arXiv 2509.19128)

Read: `pipelinerl/vllm1.py`, `pipelinerl/actor.py`, `pipelinerl/finetune/rl/__init__.py`.
- In-flight weight updates: the vLLM server calls `engine.pause_generation(mode="keep", clear_cache=False)`, receives the broadcast via a dedicated NCCL group (`model_update_group.broadcast(buffer, src=0)` then `model.load_weights`), and resumes. Existing KV cache for in-progress sequences is kept, so one sequence is generated by several weight versions with stale KV for the old prefix. Pause time is logged separately from transfer time.
- Actor admission control mirrors AReaL: `max_lag` (in samples) converts to `lag_groups = ceil(max_lag / attempts)` extra groups that may be submitted before the next weight version propagates.
- Loss: PPO-style clip with `epsilon_low/high` (0.2 default), per-token old log-probs from the rollout servers, an alternative REINFORCE branch with `ratio.clamp(0, 1+eps_high).detach()` as the weight, Schulman k3 KL against reference with log-ratio clamp. No value network by default.
- ScaleRL (arXiv 2510.13786, as summarized) found PipelineRL-8 beats PPO-off-policy on compute efficiency (the B in the scaling curve) with similar asymptote, CISPO and GSPO beat DAPO, and an FP32 LM head gives a "considerable" asymptotic boost; recipe also uses zero-variance filtering and forced length interruptions; over 400k GB200 GPU-hours total.

### 2.6 Moonshot checkpoint-engine, Mooncake, Kimi K2/K3

- `MoonshotAI/checkpoint-engine` README: `ParameterServer` colocated with inference engines; Broadcast path (H2D, then broadcast into a CUDA-IPC buffer shared with the inference engine, then the engine copies the subset it needs, pipelined, falling back to serial when GPU memory is short) and P2P path (Mooncake transfer engine sends from CPU memory of existing instances to GPUs of new instances, bucket assignment optimized per sender-receiver pair). Claims about 20 s for Kimi-K2 1T across thousands of GPUs; table: Kimi-K2 FP8 256xH20 TP16 broadcast 16.04 s, P2P 16.75 s (8 GiB buckets); default `PS_MAX_BUCKET_SIZE_GB=8`; includes a vLLM FP8 patch for weight updates.
- Kimi K2 report (arXiv 2507.20534): the report describes a colocated architecture, engine switching, system startup and agentic rollout (sections 3.3.1-3.3.4); the fetched summary did not expose numbers, so details beyond the checkpoint-engine README are unverified here.
- Kimi K3 report (arXiv 2607.24653, read via WebFetch summary of the PDF): partial rollout that "maintains an active workload of N x K trajectories" and "pauses as soon as a fraction lambda of trajectories completes"; long-context RL infra with an external KV cache pool (write-back to CPU DRAM only on GPU eviction), a rollout auto-throttling scheduler driven by active/queued request counts and KV utilization, gradient-buffer reuse during non-policy forwards; AgentENV sandboxes (Firecracker microVMs) with pause/resume, fork ("create new sandboxes from the exact original state for reward judging without side effects") and snapshot; 133 ms checkpoint, 49 ms resume, 51,219,741 sandboxes from 1,505,678 images, memory overcommit up to 6.5x; MXFP4 weights and MXFP8 activations for MoE experts in SFT and RL (quantization-aware); multi-teacher on-policy distillation reward clipped to +-Rmax. Details on routing replay and mismatch handling were not in the fetched text.

### 2.7 Other systems worth knowing (all as summarized, not code-read)

- MiniMax Forge (HF blog; M2 series report arXiv 2605.26494): Agent / Middleware (Gateway server + Data Pool) / Train-Rollout split so agents are black boxes; windowed FIFO scheduling (any completed trajectory inside window `[Ti, Ti+W-1]` can be consumed immediately, nothing outside it until the window advances) to avoid head-of-line blocking without drifting to easy samples; prefix-tree merging of multi-turn samples (reported 40x training speedup); MTP speculative decoding, prefill/decode disaggregation, global L3 KV pool; CISPO with clipped IS weight; rewards include process, task-completion-time and reward-to-go normalization. MiniMax-M1's FP32 LM-head fix (token-probability correlation about 0.9x to about 0.99x) is relayed via a secondary blog and is unverified.
- Laminar (arXiv 2510.12633): CPU relay workers decouple trainer from weight distribution (actor pushes to a master relay by RDMA and resumes; rollouts pull from colocated relay over PCIe), trajectory-level asynchrony, KV-utilization-triggered repack of straggler trajectories onto fewer replicas, heartbeat failover with a partial-response pool; up to 5.48x throughput on 1024 GPUs.
- DORA (Meituan, arXiv 2604.26256): multi-version streaming (several policy versions live on rollout instances; long trajectories finish under their original version), sliding-window staleness bound, load-balancer migration with KV reuse; 2.12x end-to-end, 6.2x in production claims.
- Seer (arXiv 2511.14617): divided rollout, context-aware scheduling (requests from the same prompt have similar lengths), grouped speculative decoding; up to 2.04x rollout throughput, 72-94% lower long-tail latency. APRIL (arXiv 2509.18521): over-provision, stop at target, recycle partial responses; 22.5% average rollout throughput gain (max 44%), up to 8% accuracy.
- Prime Intellect prime-rl / INTELLECT-3: "async, always a few steps off-policy", Environments Hub, custom Prime Sandboxes (sub-10 s startup at high concurrency), 512 H200. Their `docs/async.md` URL returned 404, so async level specifics are unverified.
- DeepSeek-V3.2 (via Raschka's summary): unbiased KL (reweight the KL term with the same IS ratio), off-policy sequence masking (drop sequences that are both negative-advantage and too far off-policy), Keep Routing (log experts at rollout, force the same routing in training), Keep Sampling Mask (store top-p/top-k mask and reapply it in loss and KL).
- Mismatch literature: Fengyao/Liu et al. "Your Efficient RL Framework Secretly Brings You Off-Policy RL Training" (TIS, token-level truncated ratio; Notion, not rendered), Liu/Li "When Speed Kills Stability" (collapse analysis; Notion), Thinking Machines "Defeating Nondeterminism" (root cause is batch invariance, not atomics; 1000 Qwen3-235B completions gave 80 unique outputs at T=0, all identical with batch-invariant kernels; about 20% matmul penalty, about 2x latency before attention optimization; KL stayed flat at 0 in RL vs 0.001 baseline), "Defeating the Training-Inference Mismatch via FP16" (arXiv 2510.26788: FP16's 10 mantissa bits vs BF16's 7 make train and inference agree, loss scaling handles range; claims TIS/MIS need about 25% extra compute and do not close the deployment gap), R3 (arXiv 2510.11370: record routing at inference and replay in training; lowers train-inference KL, outperforms GSPO and TIS on MoE, no speed loss).

## 3. What the code shows that the papers don't

1. "TIS" in slime is not the paper's single knob. `importance_weights` has `tis` (clamp, lower bound defaults to 0, so effectively truncation) and `mis` (hard mask outside [0.5, 5.0]); `mis.yaml` adds token/sequence/geometric levels, a separate rejection-sampling stage, a 1e-4 per-token veto that kills the whole sequence, and batch-mean normalization of the weights. The default `--tis-clip` is 2.0. The three-way choice (recompute old log-probs vs bypass vs decoupled) changes cost by one full forward pass over the batch.
2. Partial rollouts in slime mask the stale prefix out of the loss (`loss_mask = [0]*response_length`) instead of correcting it, whereas PipelineRL keeps the stale KV and the full trajectory in the loss and relies on clipping, and AReaL/verl store per-token versions for correction. These are three different bias/variance choices for the same feature.
3. In-flight weight updates are not free: pause/resume modes are subtly different (`in_place` makes `flush_cache` fail; `abort` bypasses the scheduler pause flag, which is why AReaL sends two pause requests; slime chooses abort-vs-in-place per sync from `flush_cache_interval`, and only for separate GPUs).
4. The MoE R3 implementation spends most of its code on validation: exactly-once consumption asserts, all-zero-layer detection for pipeline-parallel capture, and sorted vs unsorted top-k order so BF16 accumulation matches. "Same experts" is not enough for numerical agreement.
5. Weight sync cost is dominated by plumbing, not bandwidth: bucketing, `ipc_collect()`/`empty_cache()` after every bucket, a Ray lock to avoid NCCL deadlocks, expert-parallel all-gather before HF conversion, and SGLang's begin/end session so quantized layers are repacked once. slime's delta mode adds per-tensor checksums and strict version ordering so a bad base fails loudly rather than serving garbage.
6. AReaL's `StalenessManager` is just a counter formula; the hard parts are checkpoint recovery (otherwise a burst of submissions follows) and determinism (only guaranteed at staleness 0).
7. Observability is first-class: slime logs per-batch staleness from `Sample.weight_versions`, mismatch KL/PPL, and replays dumps of rollout batches into the trainer; verl logs ESS and chi-squared; these let you attribute a collapse to mismatch vs staleness vs reward bug.
8. The reward layer is already designed for slow external services: verl's three-layer rate limiter (concurrency, RPM, TPM) with class-level global state, slime's `generation_pacer`, durable queues in straw, and SGLang's router fronting independent reward servers.

## 4. Transfer to biology: general observations

Mismatch problems are smaller for most bio generators than for 30k-token reasoning models: sequences are short (SMILES about 50 tokens, proteins 100-500), so sequence-level ratios do not compound as badly, but (a) non-standard architectures (ESM3, Evo 2/StripedHyena, diffusion LMs, graph generators) are not served by SGLang/vLLM, so you may sample with the trainer's own code (bypass/no mismatch by construction), and (b) if you do use SGLang for a GPT-style pLM, run `--get-mismatch-metrics` first and use FP16 or an FP32 LM head before reaching for IS correction. The real gap in bio is staleness and reward latency, covered next.

## 5. Design notes: RL when reward is an expensive simulator or a robotic lab

Setting: policy proposes a protein sequence / molecule / protocol; the reward is ESMFold or AlphaFold-class folding (seconds to minutes per candidate on a GPU), docking (seconds to minutes on CPU), MD or FEP (GPU-hours), or an automated lab (hours to days, batch-structured, noisy, throughput-capped at, say, 96-384 samples per run). Anchors from the literature: ProteinZero (arXiv 2506.07459) runs online RAFT/GRPO against ESMFold TM-score plus an inverse-folding ddG estimator on one 8xA100 node in about 3 days, using a cheap learned stability proxy (reported 26-87x faster than physics); the RLXF Nature Communications paper (2026) closes the loop with wet-lab fluorescence on CreiLOV across five families; a 2026 arXiv study shows LLM agents genuinely learn from lab-in-the-loop feedback only when the base model is capable enough. None of these use an LLM-RL-scale async stack; the pieces below are how you would build one from slime/verl/AReaL parts.

### 5.1 Reference architecture

```
 prompts/targets -> [policy engine: SGLang or trainer-native sampler]
        | (sequence, per-token behavior logprobs, weight_versions)
        v
 [candidate store: content-addressed, durable (straw-style / DB)]
        | dedupe by hash(seq, oracle_version)
        v
 [fidelity cascade scheduler]  L0 learned surrogate (ms)  ->  L1 ESMFold/Vina (s)
        |                      L2 AF3 complex / FEP (min-h) -> L3 robotic lab (h-d)
        v
 [result store] reward, std/replicates, latency, fidelity, oracle_version, censor flag
        v
 [group assembler: window/FIFO by SUBMISSION order] -> [trainer: decoupled PPO/CISPO + TIS/MIS + selection IPW]
        v
 periodic weight publish (disk or delta; no NCCL needed) -> policy engine
```

Reuse: slime custom generate/reward hooks (`--custom-generate-function-path`, `--custom-rm-path`), `fully_async_rollout` for the worker loop, straw for durability, SGLang `weight_versions` for attribution, AReaL's capacity formula for admission, verl's `RateLimitedRewardManager` as the template for oracle quotas.

### 5.2 Principles, each tied to something in the code

1. Make the oracle a stateless, idempotent, horizontally scaled service behind a router (SGLang Model Gateway pattern; verl `RemoteRewardManager` for CPU-bound scoring). A reward call is `(sequence, oracle_version) -> result` keyed by hash; retries are safe; results are cached forever (docking and folding are deterministic enough that duplicates across groups and epochs are common).
2. Decouple generation from scoring at the group level, not the batch level. Use slime `fully_async_rollout`'s model: workers keep N groups in flight, groups with ABORTED/pending members go back to the buffer, trainer pulls completed groups. Replace "latest weights" with "any version within K".
3. Stamp everything with behavior log-probs and weight versions at sampling time (slime `rollout_log_probs`/`weight_versions`; SGLang `meta_info.weight_versions`; AReaL `versions`). With latencies of hours, staleness in versions can be tens; AReaL's log-linear proximal interpolation avoids recomputing the proximal policy across so many versions, and verl's sequence-level rejection (`seq_mean_k3`) plus MIS masks bound the variance. Choose the asymmetry deliberately: DeepSeek-V3.2 drops stale sequences only when advantage is negative; in discovery settings a rare hit is the most valuable gradient signal, so keep stale positives (with clipped weights) and be aggressive with stale negatives.
4. Use admission control sized in experiment slots, not GPU slots. AReaL's `(max_staleness + version + 1) * batch - (accepted + running)` formula generalizes: `batch` becomes the lab plate size, `running` becomes in-flight experiments, and `max_staleness` becomes the number of plates you tolerate between proposal and training.
5. Multi-fidelity cascade with over-provisioning (APRIL/oversampling idea): sample many more candidates than you can afford to score at high fidelity, score all at L0, promote top-k plus a random exploration fraction to L1/L2. The learned L0 surrogate is the "reward model" of RLHF: serve it as a normal SGLang/Triton endpoint, and periodically refit it on accumulated L1-L3 labels (this refit is where the expensive data is amortized).
6. Rebalance GPUs between policy and oracle with sleep/wake. If the oracle is GPU-based (ESMFold/AF), colocate policy and oracle workers and use SGLang `release_memory_occupation` (tags `weights`, `kv_cache`) plus verl-style dynamic hybrid scheduling (activate policy replicas only when the queue is short; remove from router, abort, then sleep) to hand GPUs to folding when the candidate queue is deep. For hours-long MD or lab latency, the trainer and sampler are mostly idle anyway, so run them small (a single node) and use disk or delta weight sync (`update_weights_from_disk`, slime delta mode) rather than NCCL groups.
7. Persist partial state. The straw pattern (durable queues for prompts, partial rollouts, completed samples) plus `state_dict`/`load_state_dict` on the rollout scheduler is what lets a run survive a week-long lab loop. Add lab-specific provenance (plate id, reagent lot, assay date) to the result record.
8. Handle fault classes separately: oracle crashes (retry, then record a typed failure), timeouts (censor, see 5.3), engine hangs (slime heartbeat restarts), and trainer failure (checkpoints; AReaL's `on_version_recovered` shows the staleness accounting bug to avoid when resuming).
9. Prevent reward hacking structurally: ensemble of non-identical oracles, a held-out oracle never used for training, `fork`-style side-effect-free grading (Kimi K3 AgentENV) for agentic setups that run simulation code, and monitoring of surrogate-vs-oracle rank correlation as a first-class metric (the bio analogue of slime's mismatch KL).

### 5.3 Ideas I consider new or under-explored (inferred; I did not find these in the surveyed code or papers)

- **Selection-bias correction with inverse-propensity weights through the existing rollout-correction hook.** In a cascade, which candidates receive a high-fidelity label depends on the surrogate score, so observed rewards are a biased sample of the policy's output. The selection probabilities are known (you made them), so treat the selection stage as part of the behavior policy: multiply the per-sequence weight by 1/p_select (clipped, with the same truncation machinery as `tis_upper_bound`, `rs_veto_threshold`, `tis_batch_normalize`) in `slime/examples/train_infer_mismatch_helper/mis.py` or verl's `rollout_corr_helper.py`. This turns "active learning filter" and "off-policy correction" into one estimator (Horvitz-Thompson style). Mark as: novel as an application; the mathematics is standard.
- **Informative-censoring-aware group assembly.** Oracle latency correlates with the outcome (small proteins fold faster; unstable systems crash early or run long; failed lab runs are flagged early). Windowed FIFO by submission order (MiniMax Forge) and the lambda-fraction pause (Kimi K3) both introduce the same fast-first bias the AReaL/APRIL authors acknowledge. Consume groups in submission order, give timed-out items an explicit censored reward (floor value, or survival-style imputation from the surrogate), and log completion-time vs reward correlation as a bias diagnostic.
- **Value-of-information filtering instead of zero-variance filtering.** Dynamic sampling (`dynamic_sampling_filter_path`; ScaleRL zero-variance filtering) drops groups whose rewards are all equal, but only after paying for the oracle. When the oracle is the cost, estimate group reward variance from the surrogate and spend high-fidelity budget only on groups where the advantage signal is likely informative or where the surrogate is uncertain. I did not find this in the surveyed frameworks.
- **Version-stamped lab results as an off-policy dataset with decoupled-PPO replay.** Store (sequence, behavior log-probs, weight versions, reward, noise estimate) permanently and re-train on the whole history every update with the AReaL proximal-interpolation trick, weighting each label by inverse measurement variance. This makes each scarce wet-lab label usable many times, unlike on-policy GRPO, and the SGLang per-token version ranges make it exact for mixed-version generations.
- **Fork-and-grade for simulators.** Adopt Kimi K3's sandbox primitives for MD/docking workflows: snapshot the simulation state at an intermediate point, fork N continuations (different seeds or protocol choices) as the group in a GRPO-style comparison, pause the sandbox while the policy decides. The group-relative baseline then compares branches from identical states, which removes a large part of the variance that otherwise plagues expensive-simulator RL. I did not find an open implementation of this for scientific simulators.
- **Oracle-drift as another behavior policy.** Assay batch effects and oracle upgrades shift the reward function; tag each result with `oracle_version` and treat cross-version reward comparisons the way slime treats cross-weight-version samples: either renormalize per batch (as ProteinZero does within a candidate pool) or bridge versions with anchor sequences re-measured every plate.

### 5.4 Concrete starting recipe

1. Single node, slime or verl (or a thin custom loop for non-GPT generators), SGLang for the policy if supported, otherwise the trainer's own sampler in bypass mode.
2. FP16 or FP32 LM head; run `--get-mismatch-metrics` for one run; add `--use-tis` with `tis_upper_bound` 2.0 only if `mismatch_kl` is non-trivial.
3. Reward function = async client to an oracle router, with a content-addressed cache and a rate limiter patterned on `RateLimitedRewardManager` (concurrency, RPM, per-lab slot budget).
4. `fully_async_rollout` style worker, `max_staleness` in plates, durable queue, per-sample version stamps, decoupled PPO or CISPO with sequence-level rejection for very stale lab data.
5. Cascade: L0 surrogate trained on L1+ labels; promote top-k plus exploration; log selection probabilities; apply IPW at train time.
6. Monitoring: surrogate/oracle rank correlation, staleness histogram (slime `compute_staleness_metrics`), completion-time vs reward correlation, ESS of importance weights (verl metrics).
