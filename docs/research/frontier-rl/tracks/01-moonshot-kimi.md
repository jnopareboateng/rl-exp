# Track 01: Moonshot AI (Kimi) -- how they do RL

Researched 2026-10-05. Evidence tags: **[V]** verified from primary source I read (code, tech report, model card); **[S]** from a page summary fetched via WebFetch (the summarizer is lossy, so treat exact numbers as likely but not byte-checked); **[I]** my inference or recollection, not verified here.

## 1. TL;DR

- Moonshot's RL line is continuous and unusually coherent: **k1.5 (Jan 2025) -> Kimi-Researcher (Jun 2025) -> K2 (Jul 2025) -> K2-Thinking (Nov 2025) -> K2.5 (Jan 2026, arXiv 2602.02276) -> K2.6 / K2.7-Code (spring-summer 2026) -> K3 (Jul 2026, 2.8T params, 1M context)**. Each report reuses the same skeleton: critic-free, outcome-reward, group-mean baseline, plus a *squared log-ratio regularizer* instead of PPO/GRPO clipping. [V]
- The core objective is **not PPO/GRPO**. k1.5/K2 use the online-mirror-descent surrogate `(r - r̄ - τ·log(πθ/π_old))²`; K2.5 rewrites it as a token-level loss with log-ratio gradient masking outside `[α, β]` plus `-τ(log πθ/π_old)²`. K3 says this per-token regularization is what lets it tolerate "extreme off-policy" data from partial rollouts. No value network, no PRM, no MCTS (explicitly argued against in k1.5). [V/S]
- **Partial rollouts are the signature systems trick**, used in every generation (k1.5, Kimi-Researcher at turn level with "at least 1.5x", K2, K3). K3 formalizes it: pause generation once a fraction λ of N×K trajectories finish, park the rest, resume them first next iteration, with sandbox state frozen (microVM pause/resume). [V]
- **Reward design is hybrid and increasingly agentic**: verifiable gyms (math, code with generated tests, SWE unit tests, kernel correctness and speed vs. a PyTorch reference), plus rubric/self-critique/tournament generative reward models for non-verifiable work (K2 self-critic -> K2.5 GRM -> K3 "agentic GRM" that must write a rubric and fill a scorepad). Length/budget control is a first-class reward term in every generation (k1.5 length penalty, K2.5 Toggle, K3 per-problem budget with −1 override). [V]
- **K3 closes the loop on environments**: knowledge-graph-guided task synthesis (a self-evolving DAG that already has "Biomedicine" and "Chemistry" nodes), a *white-box* harness composer (Kimi Code, Claude Code, Codex, OpenClaw, Hermes), verify-in-the-loop "Autonomous Execution Tasks" with public + hidden verifiers and submission budgets, and persistent multi-day mock-app worlds. This is the closest public blueprint to "RL against a slow, stateful, partially observable oracle." [V]
- **Open-source infra is the real artifact**: `checkpoint-engine` (weight sync, read in full below), Mooncake (transfer engine + store, now with `mooncake-rl` and `mooncake-reshard`), Moonlight/Muon. There is **no open RL training code** from Moonshot (no trainer, no loss file). The K2 repo is weights plus docs only. [V]
- Weight sync in practice: trainer holds a pinned CPU copy; a `ParameterServer` streams it in ~8 GiB buckets through GPU **double buffers**, NCCL-broadcasts each bucket, and every vLLM worker sees the same bucket through a **CUDA IPC handle** and copies the shards it needs via `model.load_weights`. A ZMQ REQ/REP state machine orchestrates it. Claimed ~20 s for 1T params on thousands of GPUs. [V]
- Honest caveat on K3: the report, model card and weights are public and I read the report, but specific RL hyperparameters (λ, τ, batch sizes, GPU counts beyond "a few hundred GPUs per 1M-context experiment") are not disclosed. [V]

## 2. Per-project sections

### 2.1 Kimi k1.5 (arXiv 2501.12599, Jan 2025)

**Algorithm.** Online policy mirror descent. Per problem, maximize `E[r] - τ·KL(πθ || π_θi)`; closed-form optimum is `π* ∝ π_θi · exp(r/τ)`. They fit it with the squared-residual surrogate
`L = E[(r(x,y,y*) - τ·log Z - τ·log(πθ(y,z|x)/π_θi(y,z|x)))²]`, with `τ·log Z` approximated by the sample mean reward over k rollouts. Gradient = `∇log πθ · (r - r̄) - (τ/2)·∇(log πθ/π_θi)²`, i.e. group-mean-baseline policy gradient plus a quadratic pull toward the previous iterate. [V via paper text]
- No value function: they argue credit assignment through a critic penalizes recoverable wrong steps and kills the "explore, backtrack, recover" behavior long CoT needs. No MCTS, no process RM. "Planning" happens implicitly in a 128k context. [V]
- **Length penalty**: `len_reward = λ` if correct, `min(0, λ)` if wrong, with `λ = 0.5 - (len - min_len)/(max_len - min_len)` (min/max over the k samples of that prompt); warmed up after the model has first learned plain RL. [V]
- **Sampling**: curriculum (easy to hard by labeled difficulty) and prioritized sampling with probability ∝ `1 - s_i` (per-problem success rate). [V]
- **Long2short**: model merging (weight averaging), shortest-correct-of-8 rejection sampling for SFT, DPO with shortest-correct as positive and ≥1.5x longer as negative, and a final long2short RL stage with a lowered max rollout length. [V/S]
- **Data/rewards**: code problems get test cases generated with CYaRon; a problem is kept only if ≥7 of 10 reference solutions agree on the tests and ≥9 pass the suite (~323 of ~1000 online problems survived). Math uses a CoT-augmented generative RM (98.5% on spot checks vs 84.4% for the classic binary RM trained on ~800k examples). [S]

**Infra.** Iterative-synchronous loop: master, rollout workers, replay buffer, trainer workers. **Partial rollouts**: trajectories exceeding the per-iteration token budget are saved to the replay buffer and continued next iteration; "only the current iteration requires on-policy computation," earlier segments are reused (so a trajectory's later segments are generated by newer weights). Repeat detection kills degenerate loops early. **Hybrid deployment**: Megatron and vLLM in separate containers of one pod with a checkpoint-engine sidecar; <1 min train-to-inference switch, ~10 s back; weights go to HF format in shared memory and travel via **Mooncake over RDMA**; vLLM is *killed and restarted* each phase rather than partially releasing GPU memory (better utilization and fault tolerance). [S, matches Mooncake README claim that checkpoint-engine was used in K1.5 and K2 production]

### 2.2 Kimi-Researcher (June 2025 blog, no arXiv)

Source: moonshotai.github.io/Kimi-Researcher. [S: page fetched twice via summarizer]
- **What**: a single model trained end to end with RL to do deep research with three tools: parallel real-time search, a text-based browser, and a coding tool. Average ~23 reasoning steps and >200 URLs per task. HLE 8.6% (initial) -> 26.9% pass@1 (40.17% pass@4); xbench-DeepSearch 69% avg@4. Explicitly contrasted with workflow/multi-agent pipelines and with SFT on imitated trajectories ("adapts to tool changes without manual updates").
- **Algorithm**: plain **REINFORCE**, strictly **on-policy** ("critical to generate strict on-policy data"), with **negative sample control**: some negative samples are discarded to prevent entropy collapse (they report that training otherwise degrades once negatives dominate). [S]
- **Reward**: outcome-only: *format reward* (penalizes invalid tool calls / exceeding limits) and *correctness reward* vs ground truth. **Gamma decay**: reward of step i is `r·γ^(T-i)`, so with T steps, step i receives `r·γ^(T-i)`: the longer the trajectory, the more the early steps are discounted, which pushes toward shorter, more efficient paths (among equally correct trajectories, shorter wins). (γ value not disclosed.) [S]
- **Synthetic tasks**: fully automated generation plus validation of QA pairs; two families: (a) tool-centric tasks that *require* a specific tool to be solvable, (b) reasoning-intensive tasks (math/code, hard search). [S]
- **Context management**: model learns to retain relevant info and drop documents, extending one rollout beyond 50 iterations; ablation: context-managed model used ~30% more iterations. [S]
- **Infra**: fully asynchronous server-based rollout, **turn-level partial rollout** ("at least 1.5x"), Kubernetes hybrid-cloud sandboxes speaking MCP. [S]

### 2.3 Kimi K2 (arXiv 2507.20534, Jul 2025) and K2-Thinking (Nov 2025)

- **Model**: 1T-parameter MoE, 32B active, 384 experts (8 + 1 shared), MLA, 15.5T pretrain tokens. [V from model card, S from report]
- **MuonClip** (pretraining optimizer, relevant because RL also runs on it from K2.5 on): Muon with **QK-Clip**: after each step, per head h compute `S_max^h = (1/√d)·max_{i,j}(Q_i K_j^T)` over the batch; if it exceeds τ=100, rescale `W_q, W_k` by `γ_h = min(1, τ/S_max^h)` (MLA: √γ_h on head-specific q^C/k^C, γ_h on q^R, shared rotary key untouched). Zero loss spikes over 15.5T tokens. Moonlight (below) is the earlier public Muon recipe: update RMS matched to AdamW via `0.2·√max(A,B)` scaling, weight decay, ZeRO-1 distributed Muon, ~52% of AdamW FLOPs. [S/V: the 0.2·√max(A,B) line is in `Moonlight/examples/toy_train.py` L146]
- **Agentic data synthesis pipeline** (feeds SFT and RL warm-up): 3000+ real MCP tools plus >20,000 synthetic tools generated by hierarchical domain evolution; thousands of agents = system prompt x tool subset; each task gets an explicit **rubric** (success criteria, expected tool pattern, checkpoints); trajectories simulated with LLM *user personas* and an LLM **tool simulator ("functionally equivalent to a world model")**; an LLM judge filters by rubric. Real sandboxes are used where fidelity matters (coding/SWE). [S]
- **RL**: "Verifiable Rewards Gym" (math/STEM/logic, complex instruction following with code-interpreter checks plus LLM judge plus a *hack-check layer* that catches fake compliance claims, faithfulness, coding with competition judges and GitHub PR/issue tasks using human-written unit tests mined from pretraining data, safety) plus **self-critic rubric reward** for non-verifiable tasks: the model does *pairwise* comparisons of its own outputs against core rubrics (fundamental assistant values), prescriptive rubrics (anti-reward-hacking) and human-annotated rubrics; the critic is **refined on-policy using rollouts from verifiable-reward prompts**, transferring objective signal to subjective judgment. [S]
- **Objective**: k1.5's squared mirror-descent surrogate `E[(1/K)Σ (r - r̄ - τ·log(πθ/π_old))²]`; extras: **budget control** (per-task-type max tokens, over-budget penalized), **PTX loss** (auxiliary SFT loss on curated high-quality data to prevent forgetting), **temperature decay** (high early, lower later). [S]
- **Infra**: colocated training and inference on the same workers with engine switching; a **checkpoint engine on the training nodes**: each worker holds a local shard, **broadcasts all parameters across all workers, and each inference engine picks only the shards it needs**; deliberately redundant but pipelined parameter-by-parameter so a full 1T update finishes "in under 30 seconds." Agentic rollouts use partial rollout plus separately scaled heavy environment services. Training cluster: H800 nodes, 8×400 Gbps RoCE. [S]
- **K2-Thinking (Nov 2025)**: same 1T/32B architecture, 256K context, "200-300 sequential tool calls" without intervention, **INT4 weight-only QAT on MoE experts applied in post-training** (≈2x generation speed, native INT4 serving); "Heavy mode" = 8 parallel trajectories then reflective aggregation. HLE 44.9% with tools, BrowseComp 60.2, SWE-bench Verified 71.3. The blog gives no RL algorithm details beyond QAT. [S]

### 2.4 Kimi K2.5 (arXiv 2602.02276, Jan 2026) -- first 2026 model

[S for all of section; fetched twice from arXiv HTML/PDF through the summarizer]
- **Algorithm change from K2**: token-level clipping with *gradient masking by log-ratio*: `L = E[(1/N) Σ_j Σ_i  Clip(πθ/π_old, α, β)·(r(x,y_j) - r̄(x)) - τ·(log(πθ/π_old))²]`; tokens whose log-ratio falls outside `[α, β]` get zero gradient (explicitly unlike PPO, which clips depending on advantage sign). Optimizer: MuonClip. Motivation: mitigate off-policy divergence from async/partial rollouts and train-inference mismatch.
- **Toggle (token-efficient RL)**: alternate every m iterations between Phase 0 (budget-limited: reward multiplied by an indicator that is 1 if group mean accuracy < λ *or* the response is within `budget(x)`, where budget = ρ-th percentile length of correct samples) and Phase 1 (normal, long-budget scaling). Fixes "length overfitting" of fixed budgets; 25-30% fewer output tokens at negligible loss on K2-Thinking.
- **PARL (Parallel Agent RL) / Agent Swarm**: trainable **orchestrator**, **frozen sub-agents** instantiated from fixed intermediate checkpoints (avoids credit assignment ambiguity). Tools: `create_subagent`, `assign_task`. Reward `r_PARL = λ1·r_parallel + λ2·r_finish + r_perf`, with λ1, λ2 annealed to zero: `r_parallel` fights *serial collapse*, `r_finish` fights *spurious parallelism* (spawning agents that never finish). Cost metric **CriticalSteps = Σ_t (S_main^(t) + max_i S_sub,i^(t))** so only the longest parallel branch counts. Training prompts are synthetic "wide search" (many independent sources) or "deep search" (branches with delayed aggregation). Reported: up to 4.5x lower latency, item-level F1 72.8 -> 79.0. Context sharding is framed as proactive context management (sub-agents return only relevant results).
- **Vision RL**: outcome RL on grounding/counting, chart/document, vision-STEM, with task-specific shaped rewards (soft-IoU F1 for grounding, Gaussian-weighted matching for points, rasterized polygon IoU, normalized edit distance for OCR, absolute count difference). Text benefits: MMLU-Pro 84.7 -> 86.4, GPQA-D 84.3 -> 86.4, LongBench v2 56.7 -> 58.9. **Zero-vision SFT** (text-only SFT works better than hand-built visual trajectories after 10%:90% joint pretraining).
- **GRM**: generative reward models extended to agentic trajectories, with multiple rubrics to avoid overfitting a single preference; tournament-style group reward with binary comparisons (referenced again in K3). 
- **Infra (Appendix D)**: Gym-like unified agentic env with pluggable Toolset, Judge, prompt enhancement; Rollout Manager running "up to 100,000 concurrent agent tasks" as independent async coroutines; records inference-engine logprobs for **train-inference mismatch correction**; **Decoupled Encoder Process** (vision encoder replicated and load-balanced, activations discarded, recomputed in backward) gives ~90% of text-only training efficiency.
- **K2.6** (HF card updated 19 May 2026; arXiv link in card still points to the K2.5 report): same 1T/32B shell; swarm scales from K2.5's ~100 sub-agents / 1,500 steps to **300 sub-agents / 4,000 coordinated steps**; reports 12-hour (4,000+ tool calls) and 13-hour autonomous runs and a 5-day internal monitoring agent. SWE-bench Verified 80.2. No training details published. [S]
- **K2.7-Code** (HF, 15 Jun 2026): built on K2.6, ~30% fewer thinking tokens; no RL method disclosed. [S]

### 2.5 Kimi K3 (HF + GitHub `MoonshotAI/Kimi-K3`, tech report `k3_tech_report.pdf`, July 2026)

[V: I downloaded the report and read §1, §4 (post-training), §5.3 (RL infra)]
- **Model**: 2.8T total / 104B active, 93 layers (69 Kimi Delta Attention + 24 gated MLA), Stable LatentMoE 16-of-896 experts, 1M context, MXFP4 expert weights / MXFP8 activations via QAT, MoonViT-V2. Report admits it trails Claude Fable 5 and GPT-5.6 Sol overall.
- **Three-stage post-training**: SFT cold start -> **9 RL experts = 3 domains x 3 reasoning efforts** {low, high, max} -> **Multi-Teacher On-Policy Distillation (MOPD)** into one model. Domains: (i) general (reasoning, vision, search, knowledge work, faithfulness), (ii) general agents (long-horizon assistant, deep research, writing), (iii) coding agents (SWE, kernels, web dev).
- **MOPD reward**: per-token `r = clip(sg[log π_teacher^(d,e)(y_t|x,y<t) / πθ(y_t|e,x,y<t)], -R_max, R_max)`, i.e. a clipped log-ratio to the teacher selected by (domain, effort) is used as a *dense per-token RL reward* in the same RL pipeline (so partial rollouts still work); top-k distillation variants gave no gain. 
- **Algorithm**: policy optimization "follows Kimi K2.5" with the per-token regularizer; partial rollout extended as: sample K completions for each of N prompts, stop generation when λ·N·K complete, enqueue the rest first for next iteration, dispatch a prompt for training once all K of its responses finish. Staleness is tolerated by the localized-trust-region effect of the regularizer (their claim; no ablation I saw).
- **Reasoning-effort RL**: per-problem budget `b0(x)` from the cold-start model; reward overridden to **−1** if total tokens `T(y) > τ·b0(x)` (thinking tokens for general tasks; cumulative output tokens *including tool-call arguments* for agentic tasks). Train max-effort first with large τ, then anneal τ down to get high and low experts, "human-in-the-loop" tuned per domain.
- **Agentic GRM**: for non-verifiable tasks; judge must (1) read the product, (2) write a rubric, (3) score each candidate, (4) write scores to a scorepad; tournament binary comparisons; **verbosity control**: a candidate longer than `σ·ℓ0` automatically loses.
- **Deployment-aware RL**: QAT (MXFP4/MXFP8) throughout SFT *and* RL; rollout and training share the quantization scheme, which removes train-inference mismatch from quantization. EAGLE-3 draft head fine-tuned afterward with an `LK` loss (−log of speculative acceptance rate).
- **Environments (§4.2)**: unified **white-box harness** (compose tool interfaces, system prompts, context-management strategies, skills, memories, sub-agents; instantiates Kimi Code / Claude Code / Codex / OpenClaw / Hermes or novel harnesses; randomized per task group); **knowledge-graph-guided task synthesis** (agent-grown DAG, nodes include Biomedicine, Chemistry, Physics, Math; keyword sets sampled from graph -> web retrieval -> synthesis agent emits coding/knowledge/vision tasks); **verifiable agentic problems** (deep search, professional workflows like banking/legal/data analysis, vision with a Python sandbox for crop/zoom); **kernel optimization** (CUDA/Triton/CuTe/TileLang/Gluon; zero reward if numerical error exceeds a threshold vs PyTorch reference; 0.5 reward for matching an expert kernel, rising toward 1 near hardware roofline; hack detector for CUDA-graph replay, input caching, precision reduction); **personal assistant worlds** (mock Gmail/Notion/Slack/Canvas, multi-day event streams, thousands of tool calls, millions of context tokens, per-event evaluators); **Autonomous Execution Tasks** (initial state + constrained goal + action space + budget + independent verifier; reward from verifier's judgement of *final environment state*, not agent's claim; public diagnostic verifier + hidden held-out verifier + penalty under limited submission budgets; instances: black-box system replication, quantitative factor discovery, tax auditing); **web dev** (deterministic functional/pixel checks plus model judge; reward zeroed if build fails or artifact is faked).
- **Infra for 1M-context agentic RL (§5.3)**: colocated RL keeping a 1M-context experiment "within a few hundred GPUs"; **external KV-cache pool in CPU DRAM with write-back (not write-through)** so idle prefixes evicted from GPU survive across partial-rollout iterations (KDA recurrent states offloaded with MLA blocks); training weights/optimizer states are pushed to **NVMe** after each train step to free DRAM, pool is released before training; **rollout auto-throttling** using active/queued request counts and KV utilization; **reference-model weights streamed through the policy's FP32 gradient buffers** (ZeRO-2, two VPP chunks, double-buffered prefetch). **AgentENV** microVM sandboxes (Firecracker): incremental checkpoint/resume at 133 ms / 49 ms, **pause** while waiting for model inference (can be 98% of sandbox lifetime), **fork** (judge a copy without side effects), periodic **snapshot**; OverlayBD images, 6.5x memory overcommit; **51,219,741 sandboxes across 1,505,678 images** created over K3 training and evaluation.

### 2.6 Adjacent Moonshot RL work

### 3.1 How checkpoint-engine broadcasts weights (code walk-through)

Roles: **ParameterServer (PS)**, one process per training/PS GPU rank, *colocated* with inference; **VllmColocateWorkerExtension**, injected into every vLLM worker (`--worker-extension-cls checkpoint_engine.worker.VllmColocateWorkerExtension`, `--load-format dummy` so vLLM starts without real weights while the PS loads).

1. **Register** (`ps.py::register_checkpoint`): safetensors files or in-memory `named_tensors` are packed into aligned, **pinned CPU `MemoryBuffer`s** (`pin_memory.py`). With `use_inplace_pin_memory=True`, safetensors files in `/dev/shm` are pinned *in place and then deleted* (warned in the docstring); there is also a reusable shared pool. If P2P is enabled, the same buffers are registered with Mooncake `TransferEngine.batch_register_memory`.
2. **Gather metas** (`gather_metas`): `dist.all_gather_object` of per-rank buffer metadata (tensor name/dtype/shape/offset, base pointer, host IP, GPU UUID, RDMA device) builds `_current_global_parameter_metas` and the global list of GPU UUIDs used to name ZMQ sockets. It also builds a GPU-to-RDMA-NIC topology map.
3. **Bucket planning** (`_detect_bucket_size`, `_gen_h2d_buckets`): an all-reduce(MIN) of free GPU memory × `PS_MEM_FRACTION` (default 0.9) picks the bucket size. Free memory is divided by 3 when an H2D staging buffer fits (else by 2 and fall back to serial H2D): bucket = `min(max(PS_MAX_BUCKET_SIZE_GB=8 GiB default, largest single tensor), free)`. Tensors are packed greedily into buckets per owner rank. In broadcast mode (`ranks` empty), the **owner of a bucket is also its sender**.
4. **Shared buffer + handle**: each PS rank allocates `buffer = torch.empty(2*bucket_size, uint8)` on GPU (a **double buffer**) and `ipc_handler.export(buffer)` makes a CUDA IPC handle (XPU: SYCL `ipc_memory`; NPU: torch.multiprocessing). It binds a ZMQ `REQ` socket at `ipc://@checkpoint-engine-<gpu-uuid>-<counter>.sock` and spawns a thread running `req_func`, which POSTs `{"method": "update_weights_from_ipc", "args": [socket_paths]}` to vLLM's `/collective_rpc` (`api.py::request_inference_to_update`). The PS then `send_pyobj(handle)` once.
5. **Worker attach** (`worker.py::update_weights_from_ipc`): each vLLM worker looks up the socket for *its own* GPU UUID, connects a `REP` socket, receives the IPC handle, maps the **same physical GPU memory** as a uint8 tensor, and ACKs. From then on it is a small state machine: receive list of `{name, dtype, shape, offset}` -> slice views out of the shared buffer (`_extract_weights`, zero copy) -> `model_runner.model.load_weights(weights)` (also the MTP drafter if present) -> `synchronize` -> ACK; an `Exception` payload aborts; first `None` releases/detaches the buffer; second `None` runs `process_weights_after_loading` (post-hook; this is where FP8/quant layouts are fixed) and exits.
6. **Main loop** (`_update_per_bucket`): for each round i, for each sender rank in turn: the sender copies its bucket from the pinned CPU pool to GPU (`_copy_to_buffer`, H2D, using the staging buffer so *all ranks' H2D run in parallel*) into half `gidx % 2` of the double buffer; then `dist.broadcast(buffer_b, src=receiver_rank)` (NCCL) replicates it into every rank's buffer, which every colocated vLLM worker sees through IPC. The PS blocks on `socket.recv()` for the worker ACK, `all_reduce(SUM)`s an error code (any failure aborts all ranks), then sends the metadata for that bucket. Overlap: while workers copy bucket *g* out of half A, the PS can broadcast bucket *g+1* into half B. The vLLM worker takes **only the subset it needs under its own sharding** (TP/EP layout may differ from the checkpoint's), that is the "reload" stage.
7. **Teardown**: release handles, `empty_cache`, store-based barrier (recently fixed to be reusable across updates), process groups destroyed.

**P2P mode** (`ranks=[...]`): used for new or restarted inference instances without disturbing running ones. `_assign_receiver_ranks` spreads buckets across RDMA NICs (round-robin over owner-NIC groups so each wave uses distinct NICs; receiver = lowest rank per local NIC group); a receiver reads the bucket **directly from the owner's pinned CPU memory over RDMA into its GPU staging buffer** via Mooncake `batch_transfer_sync_read`, then does the same IPC/ZMQ hand-off and a broadcast within the subgroup. Benchmarks in the README: Kimi-K2 FP8 on 256×H20 (TP16): broadcast 16.04 s with 8 GiB buckets, P2P 16.75 s; DeepSeek-V3.1 11.3 s / 11.8 s; Qwen3-235B BF16 on 8×H800 6.2 s. SGLang has a separate integration (`python -m sglang.srt.checkpoint_engine.update`), and the Mooncake README claims an SGLang RDMA P2P path took Kimi-K2 weight sync from 53 s to 7.2 s (Apr 2026 lmsys blog [S]).

### 3.2 Mooncake relevant to RL
- Transfer Engine is the RDMA/NVLink data plane used by checkpoint-engine P2P, SGLang, vLLM, TRT-LLM, NIXL. Mooncake Store holds KV cache; README (Aug 2026) says it is now a **rollout-data transfer backend in Miles** (radixark/miles, a slime-derived trainer): GET 10-14x faster than the Ray backend, PUT 1.2-1.6x on Qwen3-0.6B math rollouts, via schema expansion + bulk packing of ragged per-sample arrays into pre-registered buffers + manifest bundles [S]. `mooncake-rl/examples/rl_samples.py` is a dummy actor/rollout example whose docstrings say "in real slime..." (so the intended consumer is slime-style RL). `mooncake-reshard` is a new framework-neutral planner that computes N-D overlap transfers between *different* TP/PP/EP/DP weight layouts (weights and KV-cache), i.e. the general form of what checkpoint-engine does heuristically with "broadcast everything, let each engine pick its slice." [V for README]

## 4. What the code shows that the papers don't

1. **It is not an all-gather-then-reshard system.** The K2 report says "broadcast redundantly, each inference engine takes the shard it needs." The code makes the trick concrete: the *only* resharding logic is vLLM's own `load_weights` applied to views of a CUDA-IPC-shared GPU buffer. checkpoint-engine itself never reasons about the inference engine's TP/EP layout. That is why it needs per-engine glue (a `worker_extension_cls` for vLLM, a patch `patches/vllm_fp8.patch` for FP8 which is only tested on DeepSeek-V3.1 and Kimi-K2) and why `mooncake-reshard` now exists.
2. **The trainer is not in the loop at update time.** The PS reads from *pinned CPU copies* (either safetensors files or `named_tensors` the trainer hands over). Training-to-PS is a separate step the repo does not implement; the repo's only demo path is "read HF checkpoint files from disk." The "three-stage pipeline" (H2D, broadcast, reload) from the paper is, per the README's own Limitations section, **not fully implemented** ("could be useful where H2D and broadcast do not conflict in PCIe").
3. **Mooncake is only on the P2P path.** The default fast path is plain `torch.distributed` broadcast (NCCL/HCCL wrappers in `checkpoint_engine/distributed/`); Mooncake TE (RDMA reads from remote CPU memory) is used for dynamic joins. Earlier K1.5-era reports had Mooncake carrying the whole weight transfer.
4. **Operational details absent from papers**: 8 GiB default bucket, 3-way split of free GPU memory, NUMA binding per GPU, error propagation by all-reduce so one failed worker aborts everyone, per-update ZMQ counter synchronized with all_reduce(MIN) of the negated counter, and `--load-format dummy` + `--wait-for-initial-weights` so inference engines can boot *before* weights exist (overlapping startup with weight load).
5. **No Moonshot repo contains an RL trainer, reward code, or environments.** Everything about loss, GRM and sandboxes is report-only. The only open "RL code" artifacts are weight sync (checkpoint-engine), data transfer (Mooncake Store/Miles), and sandbox-infrastructure descriptions (AgentENV is "developed in collaboration with partners"; I did not find its repo).
6. **Naming drift**: the K2.6 model card still cites the K2.5 report; K2.7-Code is declared "built upon K2.6" with only a ~30% token-efficiency claim. For 2026 releases other than K2.5 and K3, there is no technical report to learn RL changes from.
7. **K3-specific design pressures not visible in K2.5**: RL on a model quantized to MXFP4 during RL (not post-hoc), CPU-DRAM KV pool vs optimizer-state-on-NVMe trade, and reference-model forward by borrowing gradient-buffer memory. These are memory-capacity problems of 1M-context colocated RL, not algorithm problems.

## 5. Transfer to biology

Legend: **(N)** = I think this is genuinely novel as a pairing; (E) = established idea worth borrowing.

1. **Verifiable-reward gym for molecules/proteins modeled on K3's kernel-optimization reward (N).** K3 rewards a kernel by: correctness gate vs a reference (zero if error too large) x performance relative to an expert baseline (0.5 at parity, →1 at roofline), plus a hack detector. Port directly: *design a binder/enzyme/sequence*; gate = hard constraints (valid fold, no clashes, expression/synthesis rules, ADMET filters); score = performance vs a known best design (e.g. Rosetta/AF2-ipTM/ESM-IF self-consistency, predicted affinity, docking, or measured assay) with 0.5 at "matches the reference ligand/binder" and →1 at a physical bound; a hack detector for oracle exploitation (adversarial sequences that fool a structure predictor, repeats, degenerate low-complexity). This gives a bounded, normalized reward robust across targets, which matters when oracles have different scales.
2. **Autonomous Execution Tasks as a template for lab-in-the-loop RL (N).** AET = initial state + goal + action space + submission budget + independent verifier; public diagnostic verifier for feedback, **hidden verifier** for held-out scenarios; penalty for burning submissions. Map to a design-build-test loop: agent proposes batches of constructs, a simulator/cheap assay returns public feedback (e.g. docking or a surrogate), a held-out orthogonal oracle (different folding model, an actual assay round, or a held-out experimental dataset) decides the reward. The submission budget makes sample-efficiency and "don't over-query the oracle" part of the objective. This directly addresses oracle-overfitting in protein design.
3. **Partial rollouts with sandbox pause/fork/snapshot for slow oracles (N for wet-lab).** Docking, MD, AF-multimer, free-energy calculations and wet-lab assays are slow and variable-latency, which is the same straggler problem as 1M-token agentic rollouts. Use K3's recipe: pause trajectories when a fraction λ of a group finishes, park those waiting on the oracle (the oracle job is just a persistent external state: a Slurm job id or an assay order), resume them first next iteration. Staleness is absorbed by the squared log-ratio regularizer / gradient-masked token-level clip. For wet-lab, "resume" can be days later; the trick that makes it tolerable is that the policy regularizer is local, so stale trajectories remain usable. AgentENV-style **fork** is a good analogue of "judge a design with side-effect-free counterfactual simulations."
4. **Squared-log-ratio objective instead of PPO clip for small-sample, expensive-oracle RL (E, but under-used in bio).** `(r - r̄ - τ log(πθ/π_old))²` needs no critic, no value model, a group baseline from K samples per target, and gives a built-in trust region toward the previous policy. With 4-16 samples per target and noisy oracle rewards (typical in protein design), avoiding a learned critic is attractive; the same loss is used on sequence-level (k1.5) or token-level (K2.5). Pair with k1.5's **prioritized sampling ∝ (1 − success rate)** to focus compute on hard targets and with Kimi-Dev's **drop pass@16=0 prompts, re-add by curriculum** for targets no sample can solve yet.
5. **Reward shaping for parsimony = cost-aware design (E/N).** Toggle / K3 budget overrides translate to: penalize longer sequences, more mutations, more synthesis steps, or more assay calls once accuracy clears a threshold; alternate budget-limited and unconstrained phases to avoid "budget overfitting" (Toggle). Gamma decay (Kimi-Researcher) fits multi-step retrosynthesis or experimental-protocol planning: among equally successful routes, shorter wins.
6. **Self-critique / rubric GRM for non-verifiable biology outputs (E).** Hypothesis quality, mechanism plausibility, experimental protocol soundness, literature synthesis: use K3's protocol (judge writes rubric, scores candidates, scorepad) with pairwise tournament comparisons, **a length cap that auto-loses verbose answers**, and, from K2, *refresh the critic on-policy using prompts that do have a verifiable answer* (e.g. held-out assay results) so the judge stays calibrated to ground truth.
7. **Knowledge-graph-guided task synthesis seeded from biomedicine (N for bio-RL).** K3's DAG already has Biomedicine and Chemistry branches. Do the same with UniProt/GO/ChEBI/KEGG/Reactome ontologies as the graph; keywords from sampled subgraphs retrieve papers/databases; a synthesis agent builds tasks whose answers are *checkable against a database or computed* (e.g. "which residues in this family are conserved and how would you stabilize X", "predict pathway for compound Y" with answers verified by a reaction-rule engine or a structure tool). It gives diversity and difficulty control without manual curation.
8. **PARL for parallel experiment/design swarms (N).** Orchestrator + frozen sub-agents with `r_parallel` and `r_finish` annealed to zero and a CriticalSteps cost: apply to (a) genome-wide variant interpretation (one sub-agent per gene/locus), (b) library design where sub-agents explore different scaffolds/mechanisms and the orchestrator aggregates. CriticalSteps is a natural proxy for *wall-clock lab time* (parallel plates vs serial rounds), so the same metric can price parallel wet-lab capacity.
9. **Scale-free infra pieces to reuse today**: checkpoint-engine is model-agnostic for any vLLM/SGLang-served model, so a protein LM / ESM-style generator or a 7-70B genomics LM served by vLLM can use the same IPC-broadcast pattern; for small bio models (≤1B) it is overkill, but for GenAI-for-biology with 100B+ MoE LMs the colocated + pinned-CPU + double-buffer design applies unchanged. Mooncake Store for rollout transport is useful if rollouts are heterogeneous records (sequence, coordinates, per-residue scores, assay metadata) where ragged arrays dominate. Seer's idea (siblings from the same prompt have similar lengths) should transfer to designing many sequences for one target.
10. **Hack detection as a design requirement (E, K3 shows it is mandatory).** K3 describes agents who attempt reward hacking and containers that suffered kernel panics, forcing microVM isolation and hidden verifiers. Bio oracles are more hackable than math checkers (predictors can be fooled by out-of-distribution sequences). Ship each oracle with a held-out second oracle and a degenerate-sequence detector from day one.
