# Track 06: The open-source LLM-RL framework landscape (excluding slime, verl, ROLL)

Date of survey: 2026-10-05. Code was read from shallow clones of each repo's default branch on that date. Tags: **[V]** = verified in code/docs I read; **[P]** = from a paper/blog/web page I fetched; **[I]** = my inference; **[M]** = from memory, not re-verified.

## 1. TL;DR

- The field has converged on one skeleton: Ray (or Monarch/Ray Serve) controller + vLLM/SGLang rollout servers + FSDP2/Megatron trainer + NCCL weight push, with **fully-async, version-tagged staleness control** as the 2026 default for anything agentic. AReaL, prime-rl, SkyRL, NeMo-RL, TRL (experimental), tinker-cookbook, rLLM, Trinity-RFT, Relax and Molt all expose an explicit "max staleness / max off-policy steps" knob; each drops or masks samples past it.
- The frameworks differ most in **where the environment/reward lives**. Winners for slow external oracles are those where the reward is an independent HTTP service or a user-owned async coroutine: NeMo Gym (HTTP `verify()` servers), prime-rl + verifiers (env servers with per-stage timeouts, rate limiter, adaptive concurrency), AReaL (async `arun_episode` plus an "online" proxy mode with `set_reward` posted later), tinker-cookbook (you own the `Env`), PipelineRL (`generate_rollout` coroutine), Agent Lightning (agents run as separate processes/K8s Jobs).
- **Scale ladder [V/P]**: NeMo-RL ran Nemotron-3-Ultra (550B-A55B) RL on a default shape of 64 train + 172 generation GB200 nodes (4 GPUs each, about 944 GPUs) plus Gym nodes; prime-rl trained INTELLECT-3 (106B-A12B MoE) on 512 H200 for two months and claims readiness for 1T+ MoE on 1000+ GPUs; SkyRL + Megatron trained Qwen3.5-397B-A17B; AReaL's paper scales to 512 H800 and its AReaL-SEA is a 235B-A22B MoE; Tinker (hosted) exposes up to Kimi-K2.6 1T and Inkling 975B via LoRA. TRL, OpenRLHF, ART, PipelineRL, rLLM, Agent Lightning are in the 1.5B-72B regime (OpenRLHF's README says "70B+").
- **Biology already has a foothold in these stacks**: Biomni-R0 (Stanford) used SkyRL-Agent with async rollout scheduling to hide slow tool latency; NeMo Gym ships `ether0` (FutureHouse chemistry, SMILES verifiers, plus an external retrosynthesis/solubility oracle server), `assaybench` (Genentech CRISPR-screen ranking, AnDCG@100 reward), `labbench2_vlm`, `moldetox`, `bunsenbench_chemistry_mcq`; Tinker's launch users included Stanford's Rotskoff chemistry group.
- **Dead or paused**: torchforge (Meta) - README says development paused (last commit 2026-04-23), consolidated into torchtitan; Cosmos-RL (NVIDIA) - no longer actively developed (moved to Cosmos 3). Do not build on either. Monarch itself is alive (BSD-3), but it is an actor/RDMA layer, not an RL library.
- **Recommendation for expensive-simulator / wet-lab-in-the-loop biology**: for a research group, start with **prime-rl + verifiers** (strongest slow-oracle plumbing, MoE, permissive license) or **SkyRL** (fully async, Tinker-compatible, bio precedent); use **NeMo Gym as the environment/verifier layer** (it is trainer-agnostic: NeMo-RL, verl, Unsloth, and verifiers-side tasksets all consume it); use **AReaL's online/proxy mode** when the reward arrives hours or days later from a human or lab; use **Tinker** for fast LoRA prototyping on very large models if sending data to a hosted service is acceptable. Details in section 5.

## 3. Per-project sections

### 3.1 AReaL (areal-project/AReaL; formerly inclusionAI)

**What.** Fully asynchronous RL system from Tsinghua IIIS and Ant Group's AReaL team. README (2026) positions it as "the RL bridge for LLM-based agent applications." AReaL 2.0 (2026-07-01) re-architected into independent training, inference, agent and weight-update microservices (`areal/v2/{training_service,inference_service,agent_service,weight_update}`) and a "Hermes" online RL loop; the tech report (arXiv 2607.01120) frames this as infrastructure for self-evolving deployed agents (trajectory protocol, data proxy, evolution control plane) [P].

**Algorithm.** Decoupled PPO is the core trick for stale data. `areal/utils/functional/functional.py::ppo_actor_loss_fn` takes three log-probs: current `logprobs` (pi_theta), `proximal_logprobs` (recomputed by a forward pass at train time, or log-linear approximated: `prox_logp_method`), and `old_logprobs` (behavior policy from the inference engine). The PPO ratio and clipping are computed against the proximal policy, `ratio = exp(logprobs - proximal)`, with `eps_clip`, optional `eps_clip_higher` (DAPO clip-higher), dual-clip `c_clip`, and optional sequence-level ratio (GSPO). The staleness correction is applied separately as `behave_imp_weight` = pi_prox/pi_behave, implemented as either token/sequence **masking** (rejection) or **clamping** via a `RejectionSamplingConfig`; June 2026 added **KPop** (`rejection_sampling.metric=binary_kl`, bidirectional binary-KL token masking) and an IcePop config [V]. The docs warn that decoupled loss can conflict with newer losses such as SAPO, which needs `use_decoupled_loss=False`. The loss denominator is deliberately the pre-rejection token count so that "mask mode would [not] inflate per-token gradients by N_original/N_kept" (code comment) [V]. Algorithms: GRPO, GSPO, PPO, DAPO, LitePPO, Dr.GRPO, REINFORCE++, RLOO, SAPO, IcePop, KPop, M2PO, DPO, distillation [V README].

**Staleness control.** `areal/infra/staleness_manager.py`: capacity = `min(max_concurrent_rollouts - running, (max_staleness + current_version + 1) * consumer_batch_size - (accepted + running))`. A checkpoint-recovery fix rewrites `accepted = version * consumer_bs` because otherwise resuming at version N would let the formula submit N extra batches and make staleness unbounded (docstring) [V]. Paper: eta=4 for code, eta=8 for math; the ablation covers 0-16 and unbounded; naive PPO "failed to match performance even with minimal staleness" while the decoupled objective stabilized it [P]. Interruptible generation gave 12% and 17% throughput gains in the v0.3 ablation [V blog].

**Rewards/environments.** Three agent execution modes: `inline`, `subproc`, `online` (external apps via HTTP, `/chat/completions` plus `/rl/set_reward`; sessions garbage-collected after `session_timeout_seconds=3600`; `set_reward_finish_timeout` waits for further reward updates before finalizing) [V docs/en/tutorial/online_proxy.md and cli_args.py]. `AsyncRewardWrapper` runs a sync reward function in a shared `ProcessPoolExecutor` with 15 s timeout and 3 retries. A Daytona sandbox runner exists (`areal/infra/sandbox/runner.py`).

**Scale / results.** 512 H800 in strong-scaling, 1.5B/7B/32B distilled Qwen reasoning models, 2.77x speedup over sync [P]. ASearcher (32B QwQ) trained with 100+ tool-call turns and 400k+ output tokens, +78.0% (xBench) / +34.3% (GAIA) Avg@4 [P]. AReaL-SEA: 235B-A22B MoE on tau2-bench (73.0 airline, 98.3 telecom pass@1) [P]. Backends: Megatron (EP), FSDP2, Archon (PyTorch-native, PP+EP) [V].

### 3.2 OpenRLHF

**What.** The early Ray + vLLM + DeepSpeed RLHF stack, now "agent-based, token-in-token-out." Every run, single-turn or multi-turn, goes through `AgentExecutorBase`. A single-file async option: `--train.async_enable` runs generation and training concurrently, but through a Ray queue of depth `async_queue_size` (default 1) and a `VLLMLock` that stops weight broadcast from overlapping generation, unless `partial_rollout_enable` is set (`openrlhf/trainer/ppo_trainer_async.py`) [V]. So it is **batch-level pipelining (one-step off-policy)**, not per-sample streaming.

**Algorithms/rewards.** PPO (GAE), REINFORCE++, REINFORCE++-baseline (mean baseline, no std), RLOO, GRPO (`group_norm`), Dr.GRPO, and FlashREINFORCE (2026-09; critic-free, n=1 rollout per prompt, batch-mean baseline, binary-KL trust region on vLLM logprobs) [V code: `experience_maker.py`]. I could not verify the FlashREINFORCE paper link in the README, treat the paper reference as unverified. Dynamic filtering (DAPO) uses a 0-1 `scores` channel separate from `rewards`. Reward shaping flags: DAPO overlong penalty and ProRL stop-properly penalty.

**Environment API.** `reward_func(queries, prompts, labels)` returning `{rewards, scores, extra_logs}`, or a multi-turn `AgentInstanceBase` with `reset(states)` and `step(states)` returning `rewards, scores, environment_feedback, done, sampling_params` (`examples/python/agent_func.py`) [V]. `--reward.remote_url` accepts comma-separated HTTP RM endpoints.

**Scale.** README: "70B+." A newer **Molt** backend (NVIDIA-NeMo/labs-molt) is advertised as scaling to hundreds of billions of parameters. 2026-04 added VLM and multi-turn VLM RL.

### 3.3 Hugging Face TRL and OpenEnv

**TRL (`trl` 1.15.0.dev0).** `GRPOTrainer` (3.3k lines) is the most-used trainer. Loss types: `grpo`, `dr_grpo`, `dapo` (default; normalize by active tokens in the global accumulated batch), `bnpo`, `cispo`, `sapo`, `luspo` (needs sequence-level importance sampling); `scale_rewards` defaults to "group"; `importance_sampling_level` token or sequence [V `grpo_config.py`]. vLLM modes: `colocate` (default; vLLM inside trainer process) or `server` (separate `vllm serve`, weights streamed by NCCL via `/start_weight_update`, `/update_weights`, `/finish_weight_update`; `VLLM_SERVER_DEV_MODE=1`) [V docs]. Agent features: `tools=[...]`, `rollout_func`, and `environment_factory` (one environment instance per rollout, tool methods, `reset()` can return text appended to the last user message, `get_reward()` makes the env own the reward) [V `grpo_trainer.py`]. Environment integrations: OpenEnv (native), OpenReward, Harbor under `trl/experimental/`.

**Experimental AsyncGRPOTrainer** (`trl/experimental/async_grpo/`): a rollout worker in a **separate spawned process** with `CUDA_VISIBLE_DEVICES=""` sends prompts to a vLLM server, scores, computes advantages, and pushes samples to a queue; `max_staleness` (default 4) sets how many weight updates a sample may lag; `max_inflight_tasks` default = `max_staleness * per_device_bs * grad_accum * num_processes`; weights pushed by NCCL every `weight_sync_steps`. Constraints that matter to us: FSDP2 only (no DeepSpeed), reward functions/tools/envs must be picklable, reward models on GPU silently fall back to CPU, so a GPU reward model must be served over HTTP; default trainer dtype is float32 to reduce train/inference mismatch (cites the FP16-mismatch paper) [V `async_grpo_trainer.md`, `async_grpo_config.py`]. Async tools and environment methods run on a thread pool of `max_inflight_tasks`, so "a slow tool never blocks the other in-flight vLLM requests." That is a direct statement that slow tools are a supported case.

**OpenEnv (HF + Meta; BSD-3).** Standard Gymnasium-style `reset()`/`step()`/`state()` over WebSocket, deployable as Docker or HF Space, with an `openenv` CLI. RFCs of note: 003 (MCP tool support), **004 (Rubrics: nn.Module-style composable reward objects, `forward(action, observation) -> float`, explicit support for parallel evaluation because "LLM judges and sandboxed execution are slow (100-1000ms)")**, 005/006 (agentic harnesses), 012 (Harbor capture) [V `rfcs/`]. Rubrics live server-side inside the environment, and `src/openenv/core/rubrics/trajectory.py` implements delayed (trajectory-end) scoring. About 40 env packages ship (`envs/`: chess, finqa, julia, jupyter, browsergym, coding, terminal, wildfire, sumo_rl...), none biological. The README flags it "experimental" with unstable APIs.

### 3.4 NVIDIA NeMo-RL and NeMo Gym

**NeMo-RL (v0.7.0 on 2026-07-25).** Ray-based; DTensor (FSDP2/TP/SP/CP/PP) or Megatron-Core (6D parallelism via Megatron-Bridge) trainers; vLLM, SGLang, or Megatron-native inference. Algorithms: GRPO/GSPO/DAPO/CISPO/GDPO (multi-reward decoupled normalization), PPO, on-policy distillation, MOPD (multi-teacher on-policy distillation), DPO, SFT, RM [V README]. Async GRPO (`docs/guides/async-grpo.md`): requires `vllm_cfg.async_engine: true`, `loss_fn.use_importance_sampling_correction: true` ("required for convergence"), non-colocated generation (except Megatron colocated-reshard), and `grpo.async_grpo.{max_trajectory_age_steps: 1, max_generation_failures, in_flight_weight_updates, recompute_kv_cache_after_weight_updates}` [V]. Router replay, FP8 end-to-end, speculative decoding, Muon, LoRA for GRPO on DTensor and Megatron.

**Scale evidence.** `docs/guides/nemotron-3-ultra.md`: the default launcher shape is 64 training + 172 generation + 20 Gym GB200 4-GPU nodes; one stage example allocates 64+172+4 = 240 NeMo-RL nodes plus 20 external judge nodes; teacher stages use TP=8, CP=2, EP=16 over 4 nodes per teacher; other stage presets are 128 or 224 nodes. Pipeline: SFT -> Student RLVR (GRPO) -> specialist teachers (reasoning, RLHF chat, IFBench, SWE) -> MOPD. NeMo-RL also trained Nano-3 (30B-A3B), Super (120B-A12B), Nemotron-3.5-lightning; has Day-0 Minimax-M3 and GLM-5.1 support [V].

**NeMo Gym (Apache-2.0).** "An environment is the complete system an agent interacts with: dataset, agent harness, verifier, per-task state." Gym is CPU-only HTTP servers (agent server, model server, resources server). NeMo-RL exposes vLLM as an OpenAI-compatible HTTP server (`expose_http_server: true`) and Gym calls it during rollouts, so the weight-refit machinery is invisible to environments [V `docs/design-docs/nemo-gym-integration.md`]. A resources server subclasses `SimpleResourcesServer` and implements `async verify(body) -> reward`. 145 resource-server directories include science/bio-chem ones (below). v0.5 added seven sandbox providers and `gym eval reverify` (recompute rewards from stored rollouts without re-running inference), v0.6 "preserve exact token IDs across multi-step runs with external agent harnesses" [V README]. Trainer integrations: NeMo-RL, Unsloth, verl; plus OpenEnv, Harbor, Aviary, Reasoning Gym adapters.

**Bio/chem content in Gym [V].** `resources_servers/ether0` (325 chemistry reasoning questions, 14 task types, SMILES/formula/reaction/solubility verifiers; retrosynthesis and oracle-solubility need an extra `ether0-serve` verifier server), `assaybench` (Genentech 2026 benchmark, 1,920 CRISPR screens, reward AnDCG@100 imported from the authors' own package), `labbench2_vlm` (Edison Scientific figure/table/protocol QA with LLM judge), `moldetox`, `bunsenbench_chemistry_mcq`, `frontierscience_judge`, `critpt`/`ugphysics_judge`.

### 3.5 Prime Intellect: prime-rl, verifiers, Environments Hub, INTELLECT-2/3

**INTELLECT-2 (2025-05) [P].** First globally distributed RL run of a 32B model on a permissionless network; PRIME-RL (async), **TOPLOC** (locality-sensitive-hash proofs that detect changed model/prompt/precision in untrusted inference workers, robust to GPU non-determinism, validation much faster than generation), **SHARDCAST** (HTTP tree-topology weight broadcast). Robust to up to **4 steps** of off-policy delay; length-reward for thinking budgets; online advantage filtering that drops groups with identical rewards; modified two-sided GRPO clipping and data filtering for stability. A 4x RTX 3090 machine was enough to contribute.

**INTELLECT-3 (2025-11/12) [P].** 106B-A12B MoE on GLM-4.5-Air-Base, SFT + RL on 512 H200 (64 nodes) over two months; "the future of RL is async; i.e. always a few steps off-policy"; Environments Hub with 500+ tasks versioned separately from training code; Prime Sandboxes with sub-second container start. Tech report arXiv 2512.16144.

**prime-rl (2026-10 main) [V].** Architecture: separate orchestrator (CPU, schedules episodes via `dispatcher.py`), vLLM inference (FP8, PD disaggregation, llm-d router, Mooncake KV offload), FSDP2 trainer with EP and CP; own model implementations for GLM-5 (`glm_moe_dsa`), Qwen3/3.5 MoE, MiniMax-M2, Nemotron-H, GPT-OSS, DeepSeek-V4 (config present), Laguna, Trinity. Weight transport: NCCL default, filesystem, or NIXL/ModelExpress over InfiniBand (`docs/scaling.md`).
- **Algorithm abstraction** (`docs/algorithms.md`): `[orchestrator.train.algo] type` in `grpo`, `max_rl` (advantage normalized by group **mean** not std, upweights hard prompts ~1/p), `rae` (self-play), `hierarchical_grpo` (proposer/solver), `opd`, `sft`, `opsd`, `echo` (GRPO plus CE on environment-observation tokens). The trainer is "algorithm-blind": loss = sum of `rl`, `ce`, `ref_kl` components each normalized by its own global token count; per-token weight streams are produced by the orchestrator. Different environments in one run can use different algorithms.
- **Default RL loss is IPO**, not PPO-clip: `-(1/N) sum 1(|pi - mu| <= eps) * A * pi/mu` with `eps=0.3`; the trust region is on the absolute probability change of the sampled token (not the ratio), with `mu` the behavior policy. IcePop is an option [V docs].
- **Async**: docs describe one-step overlap (inference at step n uses policy n-1), but the orchestrator config defaults `max_off_policy_steps = 8` where a rollout can span several weight updates and episodes past the bound are dropped, in-flight and queued [V `orchestrator.py:591`, `dispatcher.py` docstring]. Dispatcher: shared permit counter for train+eval, dynamic in-flight cap moved by a concurrency controller that watches vLLM KV usage, optional `AsyncLimiter(tasks_per_minute, 60)`, burst-capped refills.
- **Multi-turn merging**: "extension property" (a later turn's prompt extends the earlier tokens) lets whole multi-turn rollouts become one training sample; best-effort interleaving and discontinuous-trajectory handling otherwise; "renderers" give token-exact chat rendering.

**verifiers v1 (MIT).** The v0 API was removed. Concepts: Taskset (collection + loader; `TaskData` rows with prompt/files/references/resources plus task class with lifecycle `setup/finalize`, `@reward`, `@metric`, toolsets installed as MCP servers), Harness (program the model runs in: Claude Code, Codex, mini-swe-agent, Hermes, Pi, OpenClaw, Terminus-2, bash, browser-use, rlm), Runtime (subprocess, Docker, Apptainer, Modal, E2B, Prime), Agent (harness x model x runtime), Env (multi-agent control flow), Trace (message graph, rewards, token IDs and logprobs). `TaskTimeout` has per-task `setup`, `agent`, `finalize`, `scoring` limits; training counts a timed-out rollout as an error (excluded from the batch) [V `verifiers/v1/task.py`, `docs/training.md`]. Adapters for NeMo Gym, OpenEnv, Harbor, TextArena tasksets. The Environments Hub is the shareable layer; I found no bio environments in the repo's `environments/` (math, wiki search, wordle, etc.).

### 3.6 SkyRL (NovaSky-AI, Berkeley + Anyscale)

Repo layout: `skyrl` (unified training library, absorbing `skyrl-train` and `skyrl-tx`), `skyrl-gym` (Gymnasium-API tool-use tasks: GSM8K, AIME, LiveCodeBench, search, SQL, RLM), `skyrl-agent` (SkyRL-Agent paper arXiv 2511.16108: async dispatcher 1.55x over naive async batching; SA-SWE-32B 24.4% -> 39.4% SWE-bench Verified), `skycap`. v0.3.0 on 2026-07-16.
- **Three modes** documented in `docs/content/docs/tutorials/fully_async.mdx`: synchronous colocated; one-step-off pipelined; **fully async with in-flight weight update / multi-turn partial rollout** (pause generation, update weights, resume). Knobs: `trainer.fully_async.max_staleness_steps`, `num_parallel_generation_workers` (>= mini-batch, <= mini-batch x (staleness+1)), `sample_full_batch` (async-native DAPO dynamic sampling that drops zero-variance groups), `clear_kv_cache_on_weight_sync` default false (reuse stale KV cache, with prefix cache isolated per policy version via `generator.use_cache_salt`). Limitation: generators must use `/chat/completions` [V].
- **Tinker API on your own GPUs** (2026-02): `forward_backward`, `optim_step`, `sample`, `save/load_checkpoint` on FSDP/Megatron/vLLM; the doc claims dense and MoE models 0.5B to 200B+ with LoRA or full-parameter [V docs/tinker/overview.mdx].
- **Scale**: Mercor's APEX-Agents recipe trained **Qwen3.5-397B-A17B** with Megatron + SkyRL fully-async trainer; 12 inference nodes : 8 training nodes; concurrency capped to about 300 trajectories at a time for KV and staleness reasons (about 1,024 max concurrent trajectories from the staleness formula), Harbor sandbox verifiers plus an LLM judge with round-robin API keys for 800+ concurrent rollouts [P blog].
- **Biology**: README lists **Biomni-R0** as built on SkyRL. Biomni-R0-32B (Qwen3-32B base) and 8B: two-stage SFT on Claude-4-Sonnet rejection-sampled trajectories, then multi-turn RL with a correctness reward and a format reward, 64k context, "asynchronous rollout scheduling that minimized bottlenecks caused by external tool delays," environment execution decoupled from model inference; average 0.669 vs 0.346 base across 10 biomedical tasks (rare-disease diagnosis 0.67 vs 0.03) [P MarkTechPost; HF model card confirms "end-to-end RL with Biomni-E1 environment"]. The primary report URL returned 404 for me.

### 3.7 rLLM (Agentica)

"Agentic RL on any harness, with any backend, on any benchmark." The 2026 rewrite: `@rllm.rollout` wraps any agent (LangGraph, OpenAI Agents SDK, plain `openai.OpenAI` client pointed at a gateway `base_url`), `@rllm.evaluator` returns an `EvalOutput` reward with named `Signal`s; sandboxes (Docker, Daytona, Modal, local) with snapshot + warm-queue acceleration (`rllm/sandbox/{snapshot,warm_queue}.py`); training backends `verl`, `tinker`, `fireworks` selected by one flag; `SyncCoordinator` implements fully-async quotas `(1 + staleness_threshold) * trigger_parameter_sync_step * mini_batch_size` [V]. Because rollouts are model-gateway driven, rLLM inherits verl's MoE and scale limits (verl is another track). Headline artifacts: DeepScaleR-1.5B, DeepCoder-14B, **DeepSWE-32B**: Qwen3-32B, 64 H100 for 6 days, 4,500 R2E-Gym tasks, 512 Docker containers per RL iteration on Kubernetes, sparse reward (+1 if the patch passes tests within 5 minutes, else 0), "GRPO++" (clip-high, no KL loss, no std normalization, length normalization, leave-one-out, mask trajectories that hit context/step/timeouts, drop entropy loss), 42.2% pass@1 and 59% with test-time scaling [P Together blog].

### 3.8 OpenPipe ART (now W&B "Serverless RL")

Client/server split. Your Python app uses an OpenAI-compatible client against the ART server (vLLM serving the latest LoRA); each rollout is a `Trajectory` you assign a `reward`; groups go to the server; GRPO updates a LoRA; "Inference is blocked while training executes" (default sync loop) [V README]. There is a `pipeline_trainer` with an autotuner and a distributed trajectory queue, plus a Megatron backend with expert-parallel and routing replay for DeepSeek-V4/GLM-5.2-class models in the code tree. RULER (LLM-judge relative ranking of trajectories) is the "no reward function needed" mode. Ergonomics are the best of the group for "bolt RL onto my existing Python workflow" but scale and algorithmic breadth are lower, and the loop is LoRA-centric.

### 3.9 Meta torchforge / Monarch

torchforge = Monarch actor "services" + vLLM generator + torchtitan trainer + TorchStore weight sync + replay buffer with `off_by_n`; `apps/grpo/main.py` uses `DAPOLoss`; configs for Qwen3 1.7B/8B and Llama3 8B. **README banner: "Development in Forge has paused. LLM training at PyTorch is being consolidated in torchtitan"** (commit 2026-04-23) [V]. Monarch (BSD-3) provides actor meshes, supervision-tree fault tolerance, one-sided RDMA, and distributed tensors; it remains a plausible substrate if you write your own controller, but I would not choose torchforge for a new project. [I] The concept worth stealing is service-level fault handling ("redirecting training loads during a run").

### 3.10 Thinking Machines Tinker (+ tinker-cookbook)

Hosted training/sampling service behind a small SDK (`forward_backward`, `optim_step`, `sample`, `save_weights_and_get_sampling_client`); LoRA is the primary mode; models listed include Kimi-K2.6 (1T/32B active), Inkling (975B/41B active, TML's own model), Nemotron-3-Ultra-550B-A55B and Qwen3.5-397B-A17B (docs `tinker/models`, 29 models) [P]. The open-source cookbook (Apache-2.0) has `rl/train.py` with `AsyncConfig(max_steps_off_policy, groups_per_batch)` and streaming-minibatch modes, an `Env` ABC where `step(action_tokens)` returns `StepResult(reward, episode_done, next_observation, ...)`, `StopReason` metrics (completed, tool_stopped, max_turns, rollout_timeout...), `rollout_error_resilience`, and recipes for math, code, search/tool use, harbor, multiplayer, rubric, distillation, forecasting, `verifiers_rl`. The key architectural property for our purposes: **all environment code runs in your process on your machine**, so a 30-minute docking job or an API call to a LIMS is just an `await` inside `step`; the remote service only samples and trains. Costs: data/gradients leave your premises, LoRA-only, vendor lock-in (mitigated because SkyRL, rLLM, Trinity-RFT implement the same API). Early users included Stanford's Rotskoff chemistry group, Berkeley SkyRL, Princeton Goedel, Redwood [P].

### 3.11 Microsoft Agent Lightning v1.0

Rewritten in 2026-08 (tech report arXiv 2608.17528, which I could not read). Three parts: Trainer (verl + vLLM), API Gateway (proxies model calls, captures token data), Rollout Controller (runs agents locally or as Kubernetes Jobs) [V README]. Agents keep real harnesses, tools and control flow (zero code change). Results: Qwen3.5-9B coding agent 41.8 -> 56.4 on SWE-bench Verified with 6K samples; Qwen3.5-35B-A3B MoE 47.8 -> 61.6 with 1.8K examples via Megatron and R3 (router replay) [README]. "Asynchronous training" doc: collocated async collection with pause/drain. MIT.

### 3.12 PipelineRL (ServiceNow)

In-flight weight updates: after each optimizer step weights are broadcast to vLLM servers without halting sampling, so sequences can mix policy versions; ~2x faster learning than conventional RL on 128 H100 at 7B and 32B; matches Open-Reasoner-Zero on AIME-2024/MATH-500; simplified GRPO with no value net, no trust-region clamp, no KL/entropy by default (README) [V/P]. The user contract is two functions, `load_problems` and `async generate_rollout(cfg, llm, problem, session) -> RolloutResult`, which makes it the easiest codebase to read and modify (`pipelinerl/` is small). Last commit 2026-06-19; research-grade.

## 4. What the code shows that the papers and READMEs don't

1. **"Async" means different things.** OpenRLHF's async is a depth-1 batch queue with a lock; prime-rl's doc says one-step overlap but its config allows `max_off_policy_steps=8` with rollouts spanning updates; TRL's async trainer is in `experimental/` and requires FSDP2; NeMo-RL's async requires importance-sampling correction as a precondition ("required for convergence"). If your oracle takes longer than one trainer step, only the "fully async, per-sample, in-flight" group (AReaL, SkyRL, PipelineRL, prime-rl, NeMo-RL, Trinity-RFT, rLLM, Relax) is actually suitable.
2. **Staleness is bounded at submission, not at reward arrival [I].** AReaL's capacity formula counts accepted + running samples against `(eta + version + 1) * batch`; a slow oracle holds a "running" slot but does not shrink the formula, so real staleness at consumption can exceed eta unless the consumer also filters by version (AReaL's `dist_rollout.py` has a staleness filter hook). prime-rl does the opposite and aggressively drops stale groups (including in-flight ones when a weight update is pending), which is safe but wastes expensive oracle calls: **with a slow oracle, raise `max_off_policy_steps`, or make oracle latency smaller than K trainer steps**.
3. **Recompute-vs-reuse of old log-probs matters for staleness.** AReaL's `prox_logp_method` can approximate the proximal log-prob in log-linear fashion to skip a forward pass; NeMo-RL and SkyRL (with `docs/algorithms/off_policy_correction.mdx`) rely on TIS-style importance correction. For expensive-reward domains where each sample is precious, the decoupled-PPO route (never wasting stale samples; just masking extreme ratio tokens) is the better fit than hard-dropping.
4. **Loss normalization is a first-class bug source.** AReaL keeps the original token count as denominator after rejection masking; prime-rl normalizes each loss component by its own global (all-reduced) count; TRL's default is DAPO's global active-token normalization. If you port a reward function between frameworks, your effective learning rate changes.
5. **Reward interfaces differ in whether they permit rewards that arrive late.** AReaL online mode (`/rl/set_reward`, `set_reward_finish_timeout`), OpenEnv RFC 004 delayed rewards, Gym `reverify`, and Tinker/PipelineRL "your coroutine" are the only ones whose APIs are not "return a float from a function within one rollout."
6. **Timeout defaults assume cheap verifiers.** AReaL's `AsyncRewardWrapper` defaults to 15 s with a process pool sized `(cpu_count // device_count) // 2` (code comment: for math/code checkers); DeepSWE used a 5-minute test limit; prime-rl's `TaskTimeout.scoring` is per task. None ship defaults for hour-scale rewards.
7. **TRL's async trainer is CPU-only for rewards and defaults to float32** (config docstring), reflecting the train/inference mismatch literature; and the standard `GRPOTrainer` now has an `environment_factory` whose env instances own the reward (`get_reward`), which is the closest to a "simulator object" abstraction in the TRL ecosystem.
8. **Weight sync is the hidden scaling limit for MoE**: NeMo-RL has a dedicated "optimizing weight transfer in large MoE by 10x" line of work, sparse-delta refit and checkpoint-engine docs (`docs/design-docs/sparse-delta-refit.md`, `nccl-reshard-refit.md`); prime-rl has NIXL/ModelExpress over IB; AReaL has `awex` and a roadmap item for weight-delta updates; Tinker/ART sidestep it with LoRA adapters.
9. **Ecosystem consolidation is visible in imports**: verifiers has `tasksets/{nemo_gym,openenv,harbor,textarena}`; NeMo Gym has `resources_servers/openenv`, `responses_api_agents/harbor_agent`; TRL has openenv/openreward/harbor adapters; rLLM and Agent Lightning delegate training to verl; SkyRL and Trinity-RFT implement the Tinker API. **Environments are becoming portable across trainers**, so the right strategy is to write the biological verifier once as an HTTP/MCP/Gym/OpenEnv server.

## 5. Transfer to biology

### 5.1 Properties of bio rewards that drive the choice

(a) Latency from seconds (RDKit, ESM scoring) to minutes (docking, AF3/Boltz folding, short MD) to days (wet-lab assay). (b) Cost per evaluation high, so wasted samples are painful. (c) Throughput caps (a lab can run 96 designs/week; a folding cluster has fixed GPUs). (d) Noise, drift, and batch effects in assay rewards. (e) Reward-hacking surface (a protein generator exploiting a fast surrogate). (f) Often the policy emits a **batch/design set**, not one trajectory.

### 5.2 Which framework for which regime

| Regime | Latency | Recommended stack | Why |
|---|---|---|---|
| Cheap deterministic verifiers (SMILES validity, formula match, ether0-style tasks, motif checks) | ms-s | NeMo-RL + Gym (ether0 server exists), or prime-rl + verifiers, or TRL for small models | Mature, drop-in |
| Medium-cost oracles (docking, folding confidence, ADMET predictors, Boltz/AF), shared GPU pool | 10 s - 10 min | **prime-rl + verifiers** (rate limiter, adaptive concurrency, per-task scoring timeout) or **SkyRL** fully async or **AReaL** workflow | Per-sample async + staleness-tolerant objective; the oracle is a service behind a queue |
| Very expensive simulators (MD free-energy, cryo-EM-like pipelines) | hours | AReaL online mode, Tinker-cookbook (own `Env`), or PipelineRL coroutine, combined with a **learned surrogate reward** and periodic oracle re-calibration | Reward arrives out-of-band; train on surrogate, retrain surrogate from oracle labels |
| Wet-lab in the loop | days | Round-based "batched async": **AReaL online `set_reward`** or any framework with a file/HTTP reward queue; or Tinker/ART loop controlled by you | Design rounds, not step-wise RL; staleness measured in rounds |
| Multi-agent lab automation (LLM planning robots, instrument control) | s-hours | RLinf (real-robot hooks, human-gated learning) for control policies; SkyRL/AReaL/verifiers + Biomni-style tool harness for planner LLMs | Existing real-world pipelines |

### 5.3 Concrete designs (ideas flagged **[novel]** are, as far as I know, not published with these frameworks)

1. **Gym-style bio verifier zoo, reusable across trainers.** Package a protein/molecule oracle as a NeMo Gym `SimpleResourcesServer` (or an OpenEnv env, or a verifiers Taskset) following `ether0` and `assaybench`: `verify()` parses the model's SMILES/sequence, calls RDKit/ESMFold/Boltz/Vina through a Ray-pooled GPU service and returns a continuous reward plus decomposed metrics. Then the same server trains under NeMo-RL (large MoE), verifiers/prime-rl, or verl. Multi-reward decomposition is a good match for NeMo-RL's GDPO (group reward-decoupled normalization), which normalizes each reward channel (e.g. binding, solubility, synthesizability, novelty) separately so that no channel dominates.
2. **Oracle-latency-aware staleness: "reward-time-bucketed async" [novel].** Combine AReaL's decoupled PPO (proximal policy, behavior-policy masking) with an oracle whose latency is long and variable: instead of dropping late rollouts (prime-rl) or letting staleness grow unboundedly, track the **policy version at generation time** and apply the `behave_imp_weight`/KPop masking at consume time. Because the data was expensive, a sample that arrives 20 versions late is still usable as long as its tokens' log-ratio lies within the trust region. Add a **prompt-level scheduler that admits new design prompts only when oracle queue length is below a budget** (prime-rl's `AsyncLimiter(tasks_per_minute)` is the right primitive; AReaL's `max_concurrent_rollouts` is the other).
3. **Surrogate-then-oracle multi-fidelity reward (cascade) with `reverify` [novel in LLM-RL toolchains].** Roll out under a cheap surrogate (ESM log-likelihood, predictor ensemble), store rollouts, then re-score the top-k or a random audit subset with the expensive oracle using NeMo Gym's `gym eval reverify` (rewards recomputed from stored rollouts, no re-inference). Use disagreement between fidelities as an online reward-hacking detector and as the labels to retrain the surrogate. In NeMo-RL async mode, rewards can then be an interpolation weighted by oracle availability.
4. **Wet-lab round as a delayed-reward session.** Use AReaL's online/proxy architecture: the policy (an LLM agent proposing sequences or protocols) lives behind an OpenAI-compatible gateway; each design round opens a session; `/rl/set_reward` is called by the LIMS integration when assay readouts arrive (raise `session_timeout_seconds` far above its 3600 s default and set `set_reward_finish_timeout` > 0 for late replicate updates). Pair with a **replicate-aware reward** (mean minus lambda x SE) and rank-based advantages (GRPO within a plate) to resist assay noise. [novel as a wet-lab use of the online-RL proxy].
5. **Tinker-style "your Env, remote GPU" for sensitive but small-scale loops.** Keep sequences, assay data and oracles in your own VPC; send only token IDs and advantages to a hosted trainer, or run SkyRL's Tinker-compatible server on your own GPUs to keep the same scripts. Use `Env.step` to submit jobs to a queue and `await` results with `ROLLOUT_TIMEOUT` stop-reasons; set `AsyncConfig.max_steps_off_policy` to cover the longest expected latency.
6. **Agentic bio with real tools (Biomni-R0 pattern) at larger scale.** Biomni-R0 showed async rollout scheduling plus correctness + format rewards works for biomedical tool-use agents on 8B-32B models. With SkyRL's fully async trainer or AReaL's agent proxy, run the same pattern on MoE models (Qwen3.5-35B-A3B up to 397B-A17B) with tools such as BLAST, UniProt/Ensembl queries, bioinformatics sandboxes (Daytona/Docker/Modal/Harbor), and rubric rewards from Gym/verifiers judges, using AssayBench-like continuous rewards (AnDCG) instead of binary correctness.
7. **Proposer-solver curricula for design tasks.** prime-rl's `hierarchical_grpo` (proposers compared to other proposers; solvers only compared on the same proposed problem) is a ready-made algorithm for self-generated curricula, e.g. a proposer LLM invents mutational-scanning or retrosynthesis questions of calibrated difficulty and a solver LLM attempts them; the oracle verifies. [novel for biology].
8. **Environment-token auxiliary loss for wet-lab outputs (ECHO) [novel for bio].** prime-rl's `echo` algorithm adds cross-entropy on environment-provided tokens (tool responses) at weight alpha=0.1. In a lab-agent loop, the environment tokens are instrument outputs, assay results and literature snippets; training the model to predict them is a form of learned world model for the lab at nearly zero extra cost.
9. **Decentralized / verifiable bio RL (TOPLOC idea) [novel speculation].** INTELLECT-2's TOPLOC lets untrusted workers contribute rollouts with cheap proofs. A consortium of labs could contribute **oracle labels** (assay results) rather than rollouts; the analogous trust problem (did this lab truly run the assay with the claimed protocol?) needs experimental provenance, but the architectural template (central trainer, permissionless workers, hash-verified artifacts) transfers.
10. **Physical-lab control with RLinf (human-gated).** For the robotic layer (pipetting, plate handling, microscope autofocus) RLinf's real-world stack (Franka, dexterous hand, HG-DAgger with human interventions, async PPO) is the only open framework in this survey that treats hardware latency and human gates as first-class.

### 5.4 Final recommendation

- **Primary: prime-rl + verifiers**, with environments authored as verifiers Tasksets that call a shared bio-oracle service. Pros: per-stage timeouts, rate limiter, adaptive concurrency, MoE and large-scale evidence (INTELLECT-3), Apache/MIT, NeMo Gym/OpenEnv adapters exist. Con: stale-episode dropping needs tuning (`max_off_policy_steps`) for slow oracles.
- **Secondary / bio precedent: SkyRL** (Biomni-R0, fully async, Tinker-API compatibility, Harbor sandboxes) for agentic lab-assistant policies and quick scale-up to a 397B MoE; or **AReaL** where the staleness-aware PPO objective and the online `set_reward` mode are decisive (long, irregular reward delays).
- **Environment layer: NeMo Gym** (already has chem/bio verifiers and the `reverify` workflow), trained with NeMo-RL if you want Megatron-class MoE scaling or with prime-rl/verl otherwise.
- **Prototyping: TRL** (GRPOTrainer + `environment_factory`) for single-GPU to 8-GPU experiments with a new verifier; **Tinker** for fast LoRA tests on huge models if hosted training is acceptable.
- Avoid for new work: torchforge (paused), Cosmos-RL (inactive). Use ART only when you want the least integration effort and LoRA scale is enough.
